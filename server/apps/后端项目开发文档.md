# 佚名后端项目开发文档

> 更新时间：2026-07-08
> 范围：移动端学生/商户/家长接口、平台 Web 管理端接口、支付资金、消息、审核、状态流转和基础运营能力。
> 依据：`../docs/client-plan.md`、`../docs/admin-plan.md`、`../docs/业务链路图.md`、`../docs/待补充.md`。

## 1. 技术方案结论

后端框架已确认采用：

| 层 | 推荐技术 | 说明 |
| --- | --- | --- |
| 服务框架 | `Java 21 + Spring Boot 3.x` | 长期稳定性、事务治理、生产运维和团队协作更稳，适合资金、订单、审核和状态机复杂的业务 |
| API 风格 | `REST + OpenAPI` | 移动端、小程序和 Web 管理端都容易接入，前端可生成 TypeScript SDK |
| Web 框架 | `Spring Web MVC` | 第一版以稳定和生态成熟为主；请求线程不得执行大批量计算和慢任务 |
| 权限认证 | `Spring Security + JWT Access Token + Refresh Token` | 支持三类用户端角色、平台管理角色、商户子账号和账号状态限制 |
| 数据库 | `PostgreSQL` | 支撑交易、资金、审核、状态流、复杂筛选和后续统计 |
| 数据访问 | `MyBatis-Plus/MyBatis + 显式 SQL` | 普通 CRUD 使用 MyBatis-Plus 提效；资金、订单、锁单等关键路径使用显式 SQL、事务和行级锁 |
| 数据迁移 | `Flyway` | 数据库结构版本化，避免生产环境手工改表 |
| 缓存/锁 | `Redis + Redisson` | 验证码、登录态辅助、热点缓存、分布式锁、限流、幂等保护 |
| 定时任务 | `Quartz/XXL-JOB 或 DB Job Table + Spring Scheduler` | 自动确认、结算释放、审核倒计时、支付补偿等任务必须持久化、可重试、可追踪 |
| 对象存储 | `S3 兼容存储/阿里云 OSS/腾讯云 COS` | 身份证照片、学信网截图、商品图片、兼职图片、投诉凭证 |
| 实时消息 | `Spring WebSocket + Redis Pub/Sub/Stream` | 狩猎池、订单状态、支付异常、审核结果、待办红点 |
| 观测运维 | `Spring Boot Actuator + Micrometer + Prometheus/Grafana` | 健康检查、指标、慢接口、JVM、数据库连接池和任务队列监控 |
| 支付 | 微信支付、支付宝、余额钱包组合支付 | 支付、退款、保证金、观察期、提现统一进入资金账户模型 |

核心判断：**第一版采用 Java Spring Boot 模块化单体，不拆微服务；管理端服务和用户端服务先写在同一个后端项目里。** 当前业务仍在规则收敛阶段，订单、兼职、委托/狩猎、家教、钱包、审核、消息和举报高度耦合。用 Spring Boot 单体可以先把事务、状态机、审计、幂等和资金账本做稳，后续再按真实瓶颈拆服务。

### 1.1 为什么切换到 Java Spring Boot

佚名后端最重要的不是单接口开发速度，而是长期维护、资金安全、复杂状态机、业务量上升后的稳定性和可观测性。选择 Spring Boot 的核心理由：

- 资金、订单、退款、保证金、提现、结算依赖强事务和可追溯流水，Java/Spring 生态更成熟。
- 未来如果扩展到多学校、多城市和多团队协作，Spring Boot 的工程边界、监控、权限、安全和运维治理更稳。
- Spring 事务、连接池、线程模型、JVM 监控和生产排障能力更适合长期平台型项目。
- 对管理端审核、对接、复核、资金、举报、风控等内部系统，Java 的稳定性优先级高于前期少量开发效率损失。
- 未来要拆资金服务、消息服务、风控服务时，Spring Boot 可以平滑演进为多服务架构。

### 1.2 Java 方案下的性能与瓶颈判断

Spring Boot 和 JVM 具备较好的并发、线程、内存和生产调优能力，但当前项目的第一瓶颈仍然不会是框架本身，而是数据库、事务锁、队列、支付回调、WebSocket 连接数和管理端复杂查询。

| 瓶颈 | 第一版风险 | 处理方式 |
| --- | --- | --- |
| 数据库慢查询和事务锁 | 高 | 关键表建索引；资金和锁单路径控制事务范围；使用 `SELECT ... FOR UPDATE`；慢查询监控 |
| 钱包和支付幂等 | 高 | 支付单、退款单、提现单、结算单都使用唯一业务号和幂等表 |
| 定时任务堆积 | 中高 | 自动确认、观察期释放、支付补偿、审核倒计时进入持久化任务系统 |
| WebSocket 连接增长 | 中 | 狩猎池和消息推送使用 Redis Pub/Sub/Stream 做多节点同步 |
| 管理端复杂查询 | 中高 | 管理端查询走聚合表、分页、索引、必要时读库或分析库 |
| 图片/OCR/内容审核 | 中 | 第一版人工审核；后续 OCR、图片处理、内容审核异步化或独立服务 |
| 大批量导出 | 中 | 异步导出，生成文件后站内消息通知下载 |

请求线程规则：

- 单次请求只做参数校验、权限判断、少量状态计算、数据库事务和事件写入。
- 不在 Controller 中写业务逻辑；不在请求线程里做 OCR、大文件处理、大报表、复杂推荐或批量导出。
- 预估耗时超过 300ms、批量处理超过 100 条记录、需要生成文件或调用慢第三方服务的动作，默认进入异步任务。
- 所有异步任务必须有业务幂等键、重试次数、失败原因、死信状态和管理端查看入口。

### 1.3 服务拆分策略

第一版不拆微服务，采用一个 Spring Boot 应用承载用户端 API、管理端 API 和内部任务。

拆分优先级按真实瓶颈决定：

| 触发瓶颈 | 优先拆分方向 |
| --- | --- |
| 钱包、支付、退款、提现复杂度上升 | 独立资金服务，继续使用 Spring Boot |
| 狩猎消息、订单消息和待办红点连接数上升 | 独立消息服务或 WebSocket 网关 |
| 信用分和风控规则复杂 | 独立风控/信用服务，可用 Java 或 Python |
| 数据看板影响交易主库 | 独立数据分析服务和分析库 |
| 管理端聚合接口明显复杂 | 独立 `admin-bff`，核心领域服务仍保持统一 |

### 1.4 Java 工程纪律

Spring Boot 项目必须从第一版开始按生产系统要求落地：

- Controller 只做入参校验、权限入口和响应包装。
- Application Service 编排用例和事务。
- Domain Service 处理领域规则、状态机、金额计算和可操作动作。
- Repository/Mapper 只负责数据访问，不写业务判断。
- 所有金额使用 `BigDecimal` 和最小货币单位字段，禁止使用浮点数。
- 所有状态流转必须写审计日志和状态历史。
- 所有外部回调必须验签、幂等、可重试。
- 所有管理端操作必须记录操作人、前状态、后状态、备注、IP、设备信息和时间。

## 3. 架构原则

### 3.1 模块化单体

第一版所有模块部署为一个 Spring Boot 应用，但代码按领域拆分。

模块之间只允许通过：

- Application Service 调用
- 领域事件
- 事务脚本
- 查询聚合层

禁止跨模块直接修改对方核心表。跨模块状态变化必须通过领域服务或领域事件触发。

### 3.2 管理端服务与用户端服务拆分建议

第一版推荐：**同一个后端项目，分用户端 API 和管理端 API 两套路由。**

路由层隔离：

```text
/api/client/*       # 学生、商户、家长移动端接口
/api/admin/*        # 平台 Web 管理端接口
/api/internal/*     # 定时任务、支付回调、内部接口
```

代码层隔离：

```text
controller/client/  # 用户端接口
controller/admin/   # 管理端接口
application/        # 业务用例编排
domain/             # 领域规则和状态机
repository/         # 数据访问
```

权限层隔离：

| 接口类型 | 访问主体 | 权限重点 |
| --- | --- | --- |
| 用户端接口 | 学生、商户、家长 | 身份互斥、账号状态、本人数据、商户子账号权限 |
| 管理端接口 | 平台管理人员 | RBAC、敏感资料查看权限、操作审计、二次确认 |
| 内部接口 | 支付回调、任务队列、系统任务 | 签名校验、幂等、重试、审计 |

为什么不第一版拆成两个后端项目：

1. 购买、兼职、委托/狩猎、家教都会同时触发用户端状态和管理端审核/对接，拆项目会增加跨服务事务和事件补偿。
2. 钱包、押金、保证金、退款、提现必须保持强一致，同项目更容易用数据库事务和行级锁保证安全。
3. 第一版规则仍在高频调整，同项目可以更快改状态机、枚举、接口契约和审核动作。
4. 团队早期维护一个部署单元更稳，日志、排查、迁移和回滚更简单。

第一版落地建议：

- 同一个 `server` 项目。
- 同一个 PostgreSQL 数据库。
- 同一套领域模型和状态机。
- 用户端、管理端使用不同 Controller、DTO、权限注解和 Response View。
- 管理端接口尽量做聚合查询，不让管理端前端拼多个用户端接口。
- 所有管理端操作写入审计日志。

### 3.3 状态机后端唯一可信

以下状态必须由后端计算和校验：

- 账号状态：正常、冻结、监管、禁言、封禁
- 订单状态：待配送/备货中、配送中、已送达、待确认、已完成、退款申请中、退款中、已退款
- 兼职状态：已报名、待筛选、未通过、已确认/待签到、已签到、进行中、结算中、已结算、未签到、异常
- 委托/狩猎状态：待领取、报价待确认、待确认激活、已锁单、进行中、待发布者确认、观察期、已结算
- 家教状态：招募中、已报名、沟通中、教育服务中、结束确认、结算中、已结算
- 钱款状态：待支付、支付中、已支付、支付异常、冻结、解冻、观察期、可提现、退款中、已退款

前端只展示状态和可用动作，提交动作时由后端再次校验。

### 3.4 资金账本不可直接改余额

钱包、押金、保证金、退款、提现、兼职结算、家教结算都必须走流水。

建议资金模型：

| 模型 | 说明 |
| --- | --- |
| `WalletAccount` | 用户或商户的钱包账户 |
| `WalletLedger` | 钱包流水，所有余额变化必须有流水 |
| `FrozenFund` | 冻结金额，如押金、签到保证金、店铺信用金、观察期收入 |
| `PaymentOrder` | 三方支付或余额支付单 |
| `RefundOrder` | 退款单 |
| `WithdrawOrder` | 提现单 |
| `SettlementOrder` | 结算单，兼职/家教/狩猎收入进入观察期后再释放 |

原则：

- 余额 = 已入账流水汇总，不直接人工修改。
- 资金动作必须幂等，所有支付回调、退款回调、任务重试都用业务单号去重。
- 组合支付需要拆分支付明细，但用户侧展示一个总支付结果。
- 退款原则上实时到账，最晚 2 个工作日；退款异常必须进入消息和订单状态。

## 4. 核心模块设计

### 4.1 认证与账号

职责：

- 手机号注册登录
- 验证码
- 注册角色选择：学生、商户、家长；登录只提交手机号和验证码，由服务端按手机号识别账号角色。
- 普通身份互斥
- token 签发与刷新
- 账号状态限制

关键规则：

- 学生注册后进入信息补充中转页，可跳过。
- 家长注册后进入孩子信息补充中转页，可跳过。
- 商户注册后进入认证资料提交。
- 冻结账号登录后只允许进入解冻申请页。
- 封禁账号不可登录。

### 4.2 校园信息

职责：

- 学校
- 校区
- 楼栋
- 楼层
- 快递站
- 食堂
- 图书馆
- 校门
- 活动中心
- 常用位置块
- 自定义位置原文保留

所有发布位置优先选择管理端维护的位置块，支持自定义填写。

### 4.3 商品与购买订单

商品来源：

- 平台自营闲置
- 平台自营耗材
- 商户商品
- 商户服务

购买订单状态：

| 状态 | 说明 |
| --- | --- |
| 待配送/备货中 | 已支付或已生成订单，等待备货或接单 |
| 配送中 | 物流、人工配送、小时达或商户配送中 |
| 已送达 | 配送方或商户标记已送达 |
| 待确认 | 等待买方确认 |
| 已完成 | 主交易链路关闭 |

订单规则：

- 待确认 48 小时后自动完成。
- 已完成后 7*24 小时内可申请退款。
- 已完成退款申请需平台自营售后或商户售后同意后进入退款流程。
- 未履约订单买方申请退款立即执行。
- 商户未来仍可履约时可更新履约日期；买方不申请退款则继续等待履约。
- 已完成订单可评价、申请退款、举报/投诉。
- 评价可匿名，一条订单只能追评一次，入口在商品详情页。

### 4.4 回收

职责：

- 学生提交回收
- 品类字段
- 图片和描述
- 预估价
- 平台审核
- 质检
- 最终报价
- 同意打款
- 拒绝退回

当前仍待 P1 细化：

- 拒绝最终报价后的退回运费
- 物品损坏争议
- 打款失败
- 收款信息异常
- 平台对接结果

### 4.5 商户

职责：

- 商户认证
- 商户类型：校园店铺、个人商户、校外服务商、校企合作
- 营业执照和门店照片
- 多门店
- 员工子账号
- 店铺信用金
- 商品和服务管理
- 售后处理

账号权限：

| 账号 | 权限 |
| --- | --- |
| 主账号 | 全量内容、认证资料、资金、员工、门店、销售、兼职、营销入口 |
| 子账号 | 售后、产品咨询、商品管理与维护 |

商户商品交易责任边界为商户自售。平台负责审核、投诉复核和必要对接，不作为默认卖方。

### 4.6 兼职

职责：

- 商户/平台发布兼职
- 报名表配置
- 报名
- 筛选
- 签到
- 保证金
- 完成确认
- 结算
- 评价/举报

发布规则：

- 发布方发布时支付岗位预算。
- 可配置是否签到。
- 签到方式可选手动签到或发布方确认。
- 可配置学生签到保证金，学生报名时缴纳，签到时退还。
- 忘签到需要发起方处理。
- 学生未签到、商户未聘用均视为违约候选事件。
- 普通兼职待审核 10 分钟无人工处理时系统默认通过。

报名表：

- 快捷字段：籍贯、年龄、身高、性别、体重、近视、是否本地等。
- 支持自定义字段。
- 邮件发送报名者填写的信息给发布者邮箱，身份证脱敏，不发送身份证信息。

### 4.7 委托/狩猎

职责：

- 发布方发布委托
- 服务方开启狩猎
- 身份证和学籍人工审核
- 押金
- 信用值
- 狩猎池
- 接单/报价
- 锁单
- 履约
- 结算

规则：

- 发布方侧叫委托，服务方侧叫狩猎。
- 委托发布分为报价发布和服务发布。
- 报价发布：服务方报价，发布方选择并确认后锁单。
- 服务发布：固定服务费，服务方直接接受。
- 报价无固定有效期，直到委托被领取、报价被接受或拒绝。
- 超过委托时效仍可领取，但需发起者确认激活。
- 默认发布 24 小时后被领取时进入待确认状态，需要发布者确认委托仍有效。
- 接受委托后 2 分钟内可取消，5 分钟内可协商取消。
- 狩猎允许跨天。
- 押金从钱包统一处理，可申请退还，发布者同意后立即退还。
- 收入进入观察期，当前默认 3 天。

### 4.8 家教

职责：

- 家长绑定孩子
- 家长发布家教需求
- 学生家教资格认证
- 学生报名
- 家长筛选
- 交换电话
- 确认招募
- 教育服务中
- 完成确认
- 结算
- 评价
- 收藏学生

规则：

- 家长发布家教需求时强校验孩子信息。
- 家长可选择是否试课、试课时长、试课费用。
- 家长可查看学生绩点、学校、专业等资料。
- 家长可拒绝学生并填写理由。
- 确认学生后状态进入教育服务中。
- 完成时由学生发起完成，家长确认后结束。
- 终止或改约由一方发起费用结算，另一方确认。
- 按实际服务天数占比计算费用，不满半天按半天，超过半天按一天。
- 结算至学生监管账户，观察期后进入可提现钱包。

### 4.9 消息与待办

职责：

- 站内消息
- 红点
- 强提醒
- 普通消息
- 业务待办

规则：

- 读消息不等于业务已处理。
- 支付异常、退款异常、待确认、资格需补充、投诉处理等进入强提醒。
- 业务红点按状态闭环清除。
- 同一业务对象的重复提醒合并为一个线程或待办。

### 4.10 举报与投诉

所有角色都可以对内容、商品、服务、兼职、委托、家教提交举报或投诉。

规则：

- 审核确认违规后，违规账号可冻结。
- 冻结账号缴纳违约金或赔偿后可申请解冻。
- 解冻后进入 1 个月监管期。
- 第一版争议举证和赔付链路不展开，只保留投诉、复核、处理结果和平台联系入口。

## 5. 管理端聚合接口

示例：

```text
GET  /api/admin/workbench/summary
GET  /api/admin/audit/tasks
GET  /api/admin/audit/tasks/:id
POST /api/admin/audit/tasks/:id/approve

POST /api/admin/audit/tasks/:id/request-supplement

GET  /api/admin/campus/schools

GET  /api/admin/funds/withdrawals
```

管理端每个操作必须记录：

## 6. 定时任务与延迟任务

第一版建议采用 `DB Job Table + Spring Scheduler` 起步，任务记录落 PostgreSQL，应用定时扫描可执行任务并抢占执行；如果后续运维需要独立任务调度平台，再升级为 `Quartz` 或 `XXL-JOB`。所有任务必须持久化、可重试、可追踪、可在管理端查看处理状态。

第一版必须实现的任务：

| 任务 | 触发 | Java 落地方式 |
| --- | --- | --- |
| 订单待确认 48 小时自动完成 | 订单进入待确认 | 写入 `system_job`，到期后由 Scheduler 抢占执行 |
| 已完成订单退款窗口关闭 | 订单完成后 7*24 小时 | 到期关闭退款申请入口，保留投诉入口 |
| 普通兼职 10 分钟默认审核通过 | 兼职进入待审核 | 审核任务超时后执行默认通过，命中风险标记的不自动通过 |
| 兼职项目结束后一周自动确认 | 项目结束时间到达后 | 到期确认结束并触发结算事件 |
| 签到保证金 24 小时未确认自动退还 | 学生发起保证金退还申请 | 发起者未处理时自动解冻/退还 |
| 委托超过时效后领取进入待确认激活 | 服务方领取过期委托 | 领取后创建发起者确认激活待办 |
| 收入观察期释放 | 结算进入观察期后默认 3 天 | 到期从观察期账户释放至可提现账户 |
| 支付/退款异常补偿查询 | 支付或退款回调缺失 | 定时查询第三方支付状态并修正本地状态 |

任务表建议字段：

- `job_id`
- `job_type`
- `biz_type`
- `biz_id`
- `idempotency_key`
- `execute_at`
- `status`
- `retry_count`
- `max_retry_count`
- `locked_by`
- `locked_until`
- `last_error`
- `created_at`
- `updated_at`

所有任务必须幂等。任务执行时先按 `idempotency_key` 和业务状态判断是否已经完成，避免重复扣款、重复退款、重复结算或重复发消息。

## 7. API 契约与错误码

API 响应建议统一。Spring Boot 通过 `@RestControllerAdvice`、统一响应包装、统一异常类和错误码枚举实现：

```json
{
  "code": "OK",
  "message": "success",
  "data": {},
  "requestId": "req_xxx"
}
```

错误码按域划分：

```text
AUTH_*
ACCOUNT_*
ORDER_*
PAYMENT_*
WALLET_*
MERCHANT_*
PART_TIME_*
HUNTING_*
TUTOR_*
REPORT_*
ADMIN_*
```

前端需要依赖的标准错误：

- 未登录
- token 过期
- 角色不匹配
- 账号冻结
- 账号监管
- 账号禁言
- 账号封禁
- 信息未补充
- 认证未通过
- 支付异常
- 状态已变化
- 操作窗口已过期
- 库存不足
- 限购超出
- 余额不足

## 8. 数据安全

必须保护：

- 身份证照片
- 身份证号
- 学信网截图
- 学号
- 电话
- 孩子信息
- 营业执照
- 门店照片
- 支付流水
- 钱包流水

要求：

- 敏感字段加密或脱敏存储。
- 身份证号、手机号、学籍信息在列表中默认脱敏。
- 报名邮件不发送身份证信息，只发送报名字段，身份证脱敏。
- 对象存储使用私有桶，前端通过临时签名上传和访问。
- 管理端查看敏感资料需要权限和审计日志。

## 9. 第一阶段开发顺序

建议后端按以下顺序开发：

1. Spring Boot 工程初始化：Java 21、Spring Web、Spring Security、MyBatis、Flyway、Redis、OpenAPI、Actuator。
2. 通用基础：统一响应、错误码、异常处理、审计日志、分页、金额、时间、幂等组件。
3. 认证和权限：手机号验证码、JWT、角色互斥、账号状态、平台管理 RBAC、商户子账号权限。
4. 校园信息管理：学校、校区、楼栋、楼层、位置块。
5. 钱包基础：钱包账户、流水、冻结资金、幂等键、事务和行级锁。
6. 商品购买闭环：商品、下单、支付、订单状态、配送、售后入口。
7. 商户能力：商户认证、店铺信用金、商品管理、销售工作台、配送和消息。
8. 管理端工作台和审核中心：审核、需补充、拒绝、通过、转对接和审计。
9. 兼职闭环：发布、报名、筛选、签到、签到保证金、结算。
10. 委托/狩猎闭环：资格验证、发布、狩猎池、报价、接单、履约和观察期释放。
11. 家教闭环：家长发布、学生资格、报名、筛选、完成、结算。
12. 消息、红点、举报、投诉、账号限制闭环。
13. 数据看板、营销预留、信用分专项规则。

## 11. 验收标准

第一版后端完成标准：

- 三类移动端角色可以完整登录并进入对应首页。
- 平台管理端可以处理审核、对接、复核和基础配置。

- OpenAPI 能生成前端可用 SDK。
