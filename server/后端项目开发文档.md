# 佚名后端项目开发文档

> 更新时间：2026-07-08  
> 范围：移动端学生/商户/家长接口、平台 Web 管理端接口、支付资金、消息、审核、状态流转和基础运营能力。  
> 依据：`../docs/client-plan.md`、`../docs/admin-plan.md`、`../docs/业务链路图.md`、`../docs/待补充.md`。

## 1. 技术方案结论

第一版后端推荐采用：

| 层 | 推荐技术 | 说明 |
| --- | --- | --- |
| 服务框架 | `NestJS + TypeScript` | 与前端同语言，便于共享 DTO、枚举和接口契约；适合模块化单体 |
| API 风格 | `REST + OpenAPI` | 移动端、小程序和 Web 管理端都容易接入，便于生成前端 SDK |
| 数据库 | `PostgreSQL` | 支撑交易、资金、审核、状态流和复杂查询 |
| ORM/迁移 | `Prisma` | 类型安全、迁移清晰；关键资金操作仍需显式事务和行级锁 |
| 缓存/队列 | `Redis + BullMQ` | 消息红点、验证码、限流、延迟任务、自动确认、超时处理 |
| 对象存储 | `S3 兼容存储/阿里云 OSS/腾讯云 COS` | 身份证照片、学信网截图、商品图片、兼职图片、投诉凭证 |
| 实时消息 | `WebSocket Gateway + 站内消息表 + 轮询兜底` | 狩猎池、订单状态、支付异常、审核结果、待办红点 |
| 认证 | `JWT Access Token + Refresh Token` | 支持多端登录、角色互斥、账号状态限制 |
| 支付 | 微信支付、支付宝、余额钱包组合支付 | 支付、退款、保证金、观察期、提现统一进入资金账户模型 |

核心判断：**第一版采用模块化单体，不拆微服务；管理端服务和用户端服务先写在同一个后端项目里。** 当前业务还在规则快速收敛阶段，订单、兼职、委托/狩猎、家教、钱包、审核、消息和举报高度耦合。过早拆成两个后端项目会让状态流、资金流和审核流更难保持一致。第一版应通过清晰模块边界、路由前缀、权限守卫和领域事件解耦。

如果团队 Java/Spring Boot 经验明显强于 TypeScript，可以把服务框架替换为 `Spring Boot + MyBatis/JPA`。但在默认小团队和前端 TS 栈的前提下，`NestJS + PostgreSQL + Redis` 是更优的交付方案。

### 1.1 后端技术选型对比

本项目后端核心关注点不是单接口跑分，而是长期维护、资金安全、复杂状态机、业务量上升后的稳定性和可扩展性。对佚名来说，购买、兼职、委托/狩猎、家教、钱包、审核、消息和举报都会互相影响，后端技术选型必须优先保证结构清晰、状态一致、资金可追溯和团队可维护。

综合判断：

| 方案 | 适合度 | 适合原因 | 主要风险 | 佚名项目建议 |
| --- | --- | --- | --- | --- |
| `NestJS + TypeScript` | 第一版最优 | TypeScript 全栈、模块化清晰、开发效率高、适合订单/钱包/审核/消息等复杂业务 | 极高并发、CPU 密集任务和超大团队治理不如 Java；需要严格工程规范 | 推荐第一版主后端 |
| `Java Spring Boot` | 长期稳定性上限最强 | 生产级生态成熟、事务能力强、监控治理完善、性能稳定、适合大型团队 | 初期开发慢、样板代码多、与 React/TypeScript 前端共享类型成本更高 | 业务量显著增长后可作为核心服务拆分方向 |
| `Koa` | 不建议做主后端 | 轻量、自由、性能开销小，适合简单 API、网关或 BFF | 架构约束少，权限、校验、异常、模块边界都要自建；长期多人维护容易散 | 可用于轻量 BFF，不做核心交易服务 |
| `Python FastAPI/Django` | 不建议做核心交易后端 | 开发快，适合风控、推荐、数据分析、运营脚本、AI/OCR 等旁路能力 | 复杂交易状态机、高并发稳定性、长期类型约束和资金事务治理不如 NestJS/Java 主线 | 适合后续风控/信用分/数据服务，不做主交易后端 |

#### 1.1.1 NestJS 的优势

NestJS 适合本项目第一版，核心原因是它在 Node.js 生态里提供了足够强的工程约束：

- 模块、Controller、Provider、Guard、Pipe、Interceptor 分层清晰，适合拆分账号、商品、订单、钱包、兼职、委托/狩猎、家教、管理端等业务域。
- 与前端同为 TypeScript 技术栈，接口 DTO、枚举、状态、错误码和 OpenAPI SDK 更容易协作。
- 对 I/O 密集型业务友好，适合数据库查询、订单接口、支付回调、消息推送、审核流转和文件上传。
- 支持队列、定时任务、WebSocket、微服务通信和 OpenAPI，能覆盖第一版到中等规模的主要需求。
- 比 Koa 更有框架约束，长期维护时不容易因为个人风格差异导致代码结构失控。

本项目使用 NestJS 时必须按强工程纪律落地：

- 使用模块化单体，按领域模块拆代码。
- 使用 DTO、Pipe 和统一错误码，禁止 Controller 直接处理复杂业务。
- 使用 Guard 做角色、账号状态、商户子账号和管理端权限控制。
- 使用 Interceptor/Filter 统一日志、异常、响应结构和审计信息。
- 使用 OpenAPI 生成前端 SDK，避免前后端接口口径漂移。

#### 1.1.2 NestJS 的性能瓶颈

NestJS 本质运行在 Node.js 上，适合 I/O 密集型服务，但需要规避以下瓶颈：

| 瓶颈 | 表现 | 处理方式 |
| --- | --- | --- |
| 单进程事件循环被阻塞 | CPU 计算、同步循环、大 JSON 处理会拖慢全部请求 | CPU 密集任务拆到 Worker、队列任务或独立服务 |
| 大量定时和延迟任务堆积 | 自动确认、结算释放、支付补偿等任务变慢 | BullMQ 分队列、任务幂等、失败重试、死信队列 |
| 数据库成为瓶颈 | 慢查询、锁等待、订单/流水表膨胀 | PostgreSQL 索引、事务边界、读写分离、冷热数据归档 |
| ORM 滥用 | N+1 查询、事务不清晰、资金操作不安全 | 关键资金路径使用显式事务、行级锁和幂等键 |
| 实时连接增长 | 狩猎池、订单消息、商户消息连接数上升 | WebSocket 网关水平扩容，Redis Pub/Sub 或消息总线同步 |
| 数据看板拖慢主库 | 经营看板和统计查询影响交易链路 | 异步聚合表、事件表、定时统计、必要时独立分析库 |

第一版性能策略：

- NestJS 使用 `Fastify adapter` 作为优先方案。
- 所有支付、退款、提现、结算、自动确认、审核倒计时都必须幂等。
- 支付、退款、消息、自动确认、收入观察期释放等异步动作进入队列。
- 钱包、押金、保证金、退款、提现使用数据库事务和流水表，不直接改余额。
- 图片处理、OCR、内容审核、复杂推荐、信用分模型等 CPU 或算法类任务不放在主请求线程。

##### 当前项目是否会遇到 CPU 密集型瓶颈

结论：**第一版和中等规模阶段，大概率不会首先遇到 CPU 密集型瓶颈。** 佚名当前主链路以 I/O 密集型业务为主，包括订单读写、支付回调、钱包流水、审核状态、消息通知、图片上传、列表筛选和管理端表格查询。NestJS 适合这类场景，真正更早出现的瓶颈通常会是数据库查询、事务锁、队列堆积、对象存储、第三方支付回调、WebSocket 连接数和慢接口，而不是 Node.js CPU 算力。

但以下功能如果实现方式不当，会把 NestJS 请求线程拖入 CPU 密集场景：

| 场景 | 第一版是否会遇到 | 风险来源 | 处理建议 |
| --- | --- | --- | --- |
| 身份证/学籍 OCR 识别 | 不会，第一版采用人工审核 | 如果后续在 NestJS 请求中直接做 OCR，会阻塞事件循环 | 第一版只上传图片和截图；后续 OCR 走第三方服务、Python 服务或异步 Worker |
| 商品/兼职/投诉图片压缩与审核 | 低概率 | 后端同步压缩大图、生成多尺寸图、图片鉴黄 | 前端压缩 + 对象存储直传；后端只保存文件信息；审核异步化 |
| 信用分计算 | 第一版不会 | 如果每次接单都实时扫描大量历史记录并计算分值 | 第一版只记录信用影响事件；信用分用异步汇总或缓存快照 |
| 狩猎派单和任务匹配 | 低概率 | 复杂路径规划、实时排序、大范围多条件匹配 | 第一版只做简单筛选、信用额度校验和定向推送；复杂匹配后续放队列或独立服务 |
| 数据看板统计 | 会遇到，但更偏数据库瓶颈 | 实时聚合订单、浏览、收藏、成交、售后率、兼职转化 | 使用事件表和聚合表，定时计算；管理端查询聚合结果 |
| 大批量导出 | 可能遇到 | 同步生成 Excel/CSV、一次性加载大量数据 | 导出任务异步化，生成文件后站内消息通知下载 |
| 内容敏感词和富文本清洗 | 低概率 | 大文本同步扫描或复杂规则匹配 | 简单规则可同步；复杂审核进入异步内容审核任务 |

请求线程规则：

- 单次请求只做参数校验、权限判断、少量状态计算、数据库事务和事件写入。
- 不在 Controller 或 Service 中做大批量循环、大文件处理、OCR、复杂统计、复杂推荐或模型计算。
- 预估 CPU 计算超过 50-100ms、批量处理超过 100 条记录、需要读取大文件或生成文件的动作，默认进入队列。
- 进入队列的任务必须具备幂等键、可重试、失败记录和死信处理。

当前项目更需要优先防的不是 CPU，而是以下稳定性问题：

| 优先级 | 更可能先出现的瓶颈 | 原因 |
| --- | --- | --- |
| 1 | 数据库慢查询和事务锁 | 订单、钱包、保证金、报名、狩猎锁单都依赖强状态流转 |
| 2 | 队列堆积 | 自动确认、结算释放、审核倒计时、支付补偿、消息推送都依赖延迟任务 |
| 3 | 支付和退款幂等 | 微信、支付宝、余额组合支付会带来回调重试和状态回放 |
| 4 | WebSocket/消息连接数 | 狩猎池、订单状态、商户消息和待办红点会推高实时连接需求 |
| 5 | 管理端复杂查询 | 审核、资金、举报、商户经营看板容易出现跨表筛选 |

因此，NestJS 方案在当前项目上可行，前提是从第一版开始就把 CPU 密集任务隔离出去，并把数据库、队列、资金幂等和审计日志作为核心工程质量来做。

#### 1.1.3 Koa 的差异

Koa 的优势是轻量、自由、性能开销低，适合：

- 简单 API
- BFF 聚合层
- webhook 接收器
- 内部轻量服务
- 网关类服务

但 Koa 不适合作为佚名第一版核心交易后端：

- 不内置模块化架构，项目结构需要团队自己约定。
- 权限、校验、异常、日志、审计、OpenAPI、依赖注入都需要额外搭建。
- 业务量上升后，如果没有非常强的架构纪律，容易出现每个模块写法不同、状态流转散落、资金逻辑难追踪的问题。
- 对新成员不够友好，维护成本会随着业务复杂度上升而放大。

结论：Koa 可以作为未来轻量 BFF 或独立 webhook 服务，但不建议承接订单、钱包、兼职、委托/狩猎、家教和管理端审核这些核心业务。

#### 1.1.4 Java Spring Boot 的差异

Java Spring Boot 的长期稳定性和上限最好，尤其适合：

- 高并发 API
- 强事务和复杂账务
- 大型团队协作
- 复杂权限和审计
- 完整监控、链路追踪、限流、熔断和容量治理
- 长周期生产系统维护

如果佚名未来扩展到多城市、多学校、大量订单、高频支付、强资金对账和专门后端团队，Java Spring Boot 会比 NestJS 更适合作为核心交易和资金服务的长期底座。

但第一版选择 Java 的成本也更高：

- 初期开发速度慢于 NestJS。
- 样板代码和工程复杂度更高。
- 与 React/TypeScript 前端共享接口类型、枚举和 SDK 的成本更高。
- 在规则频繁变化阶段，迭代速度会受到影响。

结论：第一版先用 NestJS 更合适；后续如果订单、钱包、支付或风控成为独立瓶颈，可以优先把资金服务、风控服务或消息服务按 Java/Spring Boot 方向拆出。

#### 1.1.5 Python 的差异

Python 更适合作为佚名的旁路能力，而不是核心交易后端。

适合 Python 的场景：

- 信用分模型和风控评分
- OCR、身份证/学籍资料辅助识别
- 内容审核辅助
- 推荐排序
- 数据分析和运营报表
- 爬虫、脚本、批处理
- AI 能力接入

不建议 Python 做主交易后端的原因：

- 复杂状态机、资金账本、支付回调、提现和强审计链路对长期类型约束要求高。
- 高并发稳定性和生产治理上，Java 更成熟，NestJS 与前端协同更直接。
- Python 服务更适合作为独立计算或分析服务，通过队列或内部 API 与主后端交互。

结论：第一版主后端不用 Python；后续信用分、风控、OCR、推荐和数据分析可以单独建 Python 服务。

#### 1.1.6 推荐演进路线

第一阶段：`NestJS + PostgreSQL + Redis + BullMQ`

- 单体模块化。
- 用户端和管理端同一个后端项目。
- `/api/client/*`、`/api/admin/*`、`/api/internal/*` 路由隔离。
- 强制审计、幂等、事务、队列和 OpenAPI 契约。

第二阶段：NestJS 水平扩容和数据库治理

- 多实例部署。
- Redis 支撑 WebSocket 和任务队列。
- PostgreSQL 索引优化、慢查询治理和读写分离。
- 数据看板异步聚合。
- 文件、图片、OCR、推荐等重任务移出主请求链路。

第三阶段：按瓶颈拆服务

| 触发瓶颈 | 优先拆分方向 |
| --- | --- |
| 钱包、支付、退款、提现复杂度上升 | 独立资金服务，Java Spring Boot 优先 |
| 狩猎消息和订单消息连接数上升 | 独立消息服务或 WebSocket 网关 |
| 信用分和风控规则复杂 | 独立风控/信用服务，Python 或 Java |
| 数据看板影响交易主库 | 独立数据分析服务和分析库 |
| 管理端聚合接口复杂 | 独立 `admin-bff`，核心领域服务仍保持统一 |

最终建议：**当前选择 NestJS 是合理的，但要按 Java 级别的工程纪律写 NestJS；不要按轻量脚本项目写。**

## 3. 架构原则

### 3.1 模块化单体

第一版所有模块部署为一个后端应用，但代码按领域拆分。

模块之间只允许通过：

- 服务接口调用
- 领域事件
- 事务脚本
- 查询聚合层

禁止跨模块直接改对方核心表。

### 3.2 管理端服务与用户端服务拆分建议

第一版推荐：**同一个后端项目，分用户端 API 和管理端 API 两套路由。**

```text
server/
  src/modules/
    product/        # 商品领域能力
    order/          # 订单领域能力
    wallet/         # 钱包和资金领域能力
    admin/          # 管理端聚合接口、审核工作台、权限
```

路由层隔离：

```text
/api/client/*       # 学生、商户、家长移动端接口
/api/admin/*        # 平台 Web 管理端接口
/api/internal/*     # 定时任务、回调、内部接口
```

权限层隔离：

| 接口类型 | 访问主体 | 权限重点 |
| --- | --- | --- |
| 用户端接口 | 学生、商户、家长 | 身份互斥、账号状态、本人数据、商户子账号权限 |
| 管理端接口 | 平台管理人员 | RBAC、敏感资料查看权限、操作审计、二次确认 |
| 内部接口 | 支付回调、任务队列、系统任务 | 签名校验、幂等、重试、审计 |

为什么不第一版拆成两个后端项目：

1. 购买、兼职、委托/狩猎、家教都会同时触发用户端状态和管理端审核/对接，拆项目会增加大量跨服务事务和事件补偿。
2. 钱包、押金、保证金、退款、提现必须保持强一致，放在同一个后端项目中更容易用数据库事务和行级锁保证安全。
3. 第一版规则仍在高频调整，同项目可以更快改状态机、枚举、接口契约和审核动作。
4. 团队早期维护一个部署单元更稳，日志、排查、迁移和回滚更简单。

什么时候再考虑拆分：

| 触发条件 | 拆分方式 |
| --- | --- |
| 管理端复杂度明显上升，审核/运营团队频繁改功能 | 先拆 `admin-bff`，保留核心领域服务不拆 |
| 用户端流量远高于管理端，部署节奏冲突明显 | 用户端 API 和管理端 API 分开部署，但共享领域包和数据库迁移策略 |
| 资金、风控、消息成为独立能力 | 再拆钱包服务、风控服务、消息服务 |
| 有独立团队维护管理端和用户端 | 再按团队边界拆仓库或服务 |

第一版落地建议：

- 同一个 `server` 项目。
- 同一个 PostgreSQL 数据库。
- 同一套领域模型和状态机。
- 用户端、管理端使用不同 Controller、DTO、权限 Guard。
- 管理端接口尽量做聚合查询，不让管理端前端拼多个用户端接口。
- 所有管理端操作写入审计日志。

### 3.3 状态机后端唯一可信

以下状态必须由后端计算和校验：

- 账号状态：正常、冻结、监管、禁言、封禁
- 订单状态：待配送/备货中、配送中、已送达、待确认、已完成、退款申请中、退款中、已退款
- 兼职状态：已报名、待筛选、未通过、已确认/待签到、已签到、进行中、结算中、已结算、未签到、异常
- 委托/狩猎状态：待领取、报价待确认、待确认激活、已锁单、进行中、待发布者确认、观察期、已结算
- 家教状态：招募中、已报名、沟通中、教育服务中、结束确认、结算中、已结算
- 钱款状态：待支付、支付中、已支付、支付异常、冻结、解冻、观察期、可提现、退款中、已退款

前端只展示状态和可用动作，提交动作时由后端再次校验。

### 3.4 资金账本不可直接改余额

钱包、押金、保证金、退款、提现、兼职结算、家教结算都必须走流水。

建议资金模型：

| 模型 | 说明 |
| --- | --- |
| `WalletAccount` | 用户或商户的钱包账户 |
| `WalletLedger` | 钱包流水，所有余额变化必须有流水 |
| `FrozenFund` | 冻结金额，如押金、签到保证金、店铺信用金、观察期收入 |
| `PaymentOrder` | 三方支付或余额支付单 |
| `RefundOrder` | 退款单 |
| `WithdrawOrder` | 提现单 |
| `SettlementOrder` | 结算单，兼职/家教/狩猎收入进入观察期后再释放 |

原则：

- 余额 = 已入账流水汇总，不直接人工修改。
- 资金动作必须幂等，所有支付回调、退款回调、任务重试都用业务单号去重。
- 组合支付需要拆分支付明细，但用户侧展示一个总支付结果。
- 退款原则上实时到账，最晚 2 个工作日；退款异常必须进入消息和订单状态。

## 4. 核心模块设计

### 4.1 认证与账号

职责：

- 手机号注册登录
- 验证码
- 角色选择：学生、商户、家长
- 普通身份互斥
- token 签发与刷新
- 账号状态限制

关键规则：

- 学生注册后进入信息补充中转页，可跳过。
- 家长注册后进入孩子信息补充中转页，可跳过。
- 商户注册后进入认证资料提交。
- 冻结账号登录后只允许进入解冻申请页。
- 封禁账号不可登录。

### 4.2 校园信息

职责：

- 学校
- 校区
- 楼栋
- 楼层
- 快递站
- 食堂
- 图书馆
- 校门
- 活动中心
- 常用位置块
- 自定义位置原文保留

所有发布位置优先选择管理端维护的位置块，支持自定义填写。

### 4.3 商品与购买订单

商品来源：

- 平台自营闲置
- 平台自营耗材
- 商户商品
- 商户服务

购买订单状态：

| 状态 | 说明 |
| --- | --- |
| 待配送/备货中 | 已支付或已生成订单，等待备货或接单 |
| 配送中 | 物流、人工配送、小时达或商户配送中 |
| 已送达 | 配送方或商户标记已送达 |
| 待确认 | 等待买方确认 |
| 已完成 | 主交易链路关闭 |

订单规则：

- 待确认 48 小时后自动完成。
- 已完成后 7*24 小时内可申请退款。
- 已完成退款申请需平台自营售后或商户售后同意后进入退款流程。
- 未履约订单买方申请退款立即执行。
- 商户未来仍可履约时可更新履约日期；买方不申请退款则继续等待履约。
- 已完成订单可评价、申请退款、举报/投诉。
- 评价可匿名，一条订单只能追评一次，入口在商品详情页。

### 4.4 回收

职责：

- 学生提交回收
- 品类字段
- 图片和描述
- 预估价
- 平台审核
- 质检
- 最终报价
- 同意打款
- 拒绝退回

当前仍待 P1 细化：

- 拒绝最终报价后的退回运费
- 物品损坏争议
- 打款失败
- 收款信息异常
- 平台对接结果

### 4.5 商户

职责：

- 商户认证
- 商户类型：校园店铺、个人商户、校外服务商、校企合作
- 营业执照和门店照片
- 多门店
- 员工子账号
- 店铺信用金
- 商品和服务管理
- 售后处理

账号权限：

| 账号 | 权限 |
| --- | --- |
| 主账号 | 全量内容、认证资料、资金、员工、门店、销售、兼职、营销入口 |
| 子账号 | 售后、产品咨询、商品管理与维护 |

商户商品交易责任边界为商户自售。平台负责审核、投诉复核和必要对接，不作为默认卖方。

### 4.6 兼职

职责：

- 商户/平台发布兼职
- 报名表配置
- 报名
- 筛选
- 签到
- 保证金
- 完成确认
- 结算
- 评价/举报

发布规则：

- 发布方发布时支付岗位预算。
- 可配置是否签到。
- 签到方式可选手动签到或发布方确认。
- 可配置学生签到保证金，学生报名时缴纳，签到时退还。
- 忘签到需要发起方处理。
- 学生未签到、商户未聘用均视为违约候选事件。
- 普通兼职待审核 10 分钟无人工处理时系统默认通过。

报名表：

- 快捷字段：籍贯、年龄、身高、性别、体重、近视、是否本地等。
- 支持自定义字段。
- 邮件发送报名者填写的信息给发布者邮箱，身份证脱敏，不发送身份证信息。

### 4.7 委托/狩猎

职责：

- 发布方发布委托
- 服务方开启狩猎
- 身份证和学籍人工审核
- 押金
- 信用值
- 狩猎池
- 接单/报价
- 锁单
- 履约
- 结算

规则：

- 发布方侧叫委托，服务方侧叫狩猎。
- 委托发布分为报价发布和服务发布。
- 报价发布：服务方报价，发布方选择并确认后锁单。
- 服务发布：固定服务费，服务方直接接受。
- 报价无固定有效期，直到委托被领取、报价被接受或拒绝。
- 超过委托时效仍可领取，但需发起者确认激活。
- 默认发布 24 小时后被领取时进入待确认状态，需要发布者确认委托仍有效。
- 接受委托后 2 分钟内可取消，5 分钟内可协商取消。
- 狩猎允许跨天。
- 押金从钱包统一处理，可申请退还，发布者同意后立即退还。
- 收入进入观察期，当前默认 3 天。

### 4.8 家教

职责：

- 家长绑定孩子
- 家长发布家教需求
- 学生家教资格认证
- 学生报名
- 家长筛选
- 交换电话
- 确认招募
- 教育服务中
- 完成确认
- 结算
- 评价
- 收藏学生

规则：

- 家长发布家教需求时强校验孩子信息。
- 家长可选择是否试课、试课时长、试课费用。
- 家长可查看学生绩点、学校、专业等资料。
- 家长可拒绝学生并填写理由。
- 确认学生后状态进入教育服务中。
- 完成时由学生发起完成，家长确认后结束。
- 终止或改约由一方发起费用结算，另一方确认。
- 按实际服务天数占比计算费用，不满半天按半天，超过半天按一天。
- 结算至学生监管账户，观察期后进入可提现钱包。

### 4.9 消息与待办

职责：

- 站内消息
- 红点
- 强提醒
- 普通消息
- 业务待办

规则：

- 读消息不等于业务已处理。
- 支付异常、退款异常、待确认、资格需补充、投诉处理等进入强提醒。
- 业务红点按状态闭环清除。
- 同一业务对象的重复提醒合并为一个线程或待办。

### 4.10 举报与投诉

所有角色都可以对内容、商品、服务、兼职、委托、家教提交举报或投诉。

规则：

- 审核确认违规后，违规账号可冻结。
- 冻结账号缴纳违约金或赔偿后可申请解冻。
- 解冻后进入 1 个月监管期。
- 第一版争议举证和赔付链路不展开，只保留投诉、复核、处理结果和平台联系入口。

## 5. 管理端聚合接口

Web 管理端建议不直接拼接大量普通用户端接口，而是提供管理端聚合接口。

示例：

```text
GET  /admin/workbench/summary
GET  /admin/audit/tasks
GET  /admin/audit/tasks/:id
POST /admin/audit/tasks/:id/approve
POST /admin/audit/tasks/:id/reject
POST /admin/audit/tasks/:id/request-supplement

GET  /admin/campus/schools
POST /admin/campus/schools
POST /admin/campus/locations/import

GET  /admin/funds/ledgers
GET  /admin/funds/withdrawals
POST /admin/funds/withdrawals/:id/approve

GET  /admin/reports
POST /admin/reports/:id/resolve
```

管理端每个操作必须记录：

- 操作人
- 操作角色
- 操作对象
- 前状态
- 后状态
- 备注
- IP/设备信息
- 操作时间

## 6. 定时任务与延迟任务

第一版必须实现的任务：

| 任务 | 触发 |
| --- | --- |
| 订单待确认 48 小时自动完成 | 订单进入待确认 |
| 已完成订单退款窗口关闭 | 订单完成后 7*24 小时 |
| 普通兼职 10 分钟默认审核通过 | 兼职进入待审核 |
| 兼职项目结束后一周自动确认 | 项目结束时间到达后 |
| 签到保证金 24 小时未确认自动退还 | 学生发起保证金退还申请 |
| 委托超过时效后领取进入待确认激活 | 服务方领取过期委托 |
| 收入观察期释放 | 结算进入观察期后默认 3 天 |
| 支付/退款异常补偿查询 | 支付或退款回调缺失 |

所有任务必须幂等。

```json
  "code": "OK",
  "message": "success",
  "data": {},
  "requestId": "req_xxx"
}
```

错误码按域划分：

```text
AUTH_*
ACCOUNT_*
ORDER_*
PAYMENT_*
WALLET_*
MERCHANT_*
PART_TIME_*
HUNTING_*
TUTOR_*
REPORT_*
ADMIN_*
```

前端需要依赖的标准错误：

- 未登录
- token 过期
- 角色不匹配
- 账号冻结
- 账号监管
- 账号禁言
- 账号封禁
- 信息未补充
- 认证未通过
- 支付异常

- 操作窗口已过期
- 库存不足
- 限购超出
- 余额不足

## 8. 数据安全

必须保护：

- 身份证照片
- 身份证号
- 学信网截图
- 学号
- 电话
- 孩子信息
- 营业执照
- 门店照片
- 支付流水
- 钱包流水

要求：

- 敏感字段加密或脱敏存储。
- 身份证号、手机号、学籍信息在列表中默认脱敏。
- 报名邮件不发送身份证信息，只发送报名字段，身份证脱敏。
- 对象存储使用私有桶，前端通过临时签名上传和访问。
- 管理端查看敏感资料需要权限和审计日志。

## 9. 第一阶段开发顺序

2. 认证、角色、账号状态、短信验证码、token。
3. 校园信息管理。
4. 商品、下单、支付、订单状态、售后入口。
5. 钱包、流水、退款、提现基础。
6. 商户认证、商品管理、销售工作台、配送。
7. 管理端工作台和审核中心。
8. 兼职发布、报名、筛选、签到、保证金、结算。
9. 委托/狩猎资格、发布、狩猎池、报价、接单、履约。
10. 家教需求、学生资格、报名、筛选、完成、结算。
11. 消息、红点、举报、投诉、账号限制闭环。
12. 数据看板、营销预留、信用分专项规则。

## 11. 验收标准

第一版后端完成标准：

- 三类移动端角色可以完整登录并进入对应首页。
