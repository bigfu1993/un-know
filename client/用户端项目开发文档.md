# 佚名用户端项目开发文档

> 更新时间：2026-07-08  
> 项目根目录：`D:\code\un-know`  
> 目录定位：`client` 仅承载学生、商户、家长移动端用户项目，覆盖原生 App、微信小程序和 H5。  
> 依据：`../docs/client-plan.md`、`../docs/业务链路图.md`、`../docs/待补充.md`。

## 1. 技术方案结论

用户端第一版已确认采用：

| 层 | 推荐技术 | 说明 |
| --- | --- | --- |
| 微信小程序 | `Taro + React + TypeScript` | 重点承接校园轻量获客、浏览、下单、报名和基础交易 |
| H5 | `React + Vite + TypeScript` | 重点承接活动投放、分享访问、轻量浏览、临时下单和 Web 容器访问 |
| 原生 App | `React Native + Expo/React Native CLI + TypeScript` | 重点承接高频用户、商户经营、狩猎实时接单、推送和更强原生体验 |
| 共享核心 | `TypeScript packages` | 共享接口 SDK、领域枚举、状态机、金额/时间工具、表单校验和业务 hooks |
| 状态管理 | `Zustand + TanStack Query` | Zustand 管理登录身份、账号状态、草稿和端侧状态；TanStack Query 管理服务端数据缓存 |
| 请求层 | `ofetch/axios 封装` | 统一 token、角色、错误码、支付异常、账号限制和接口重试 |
| 表单校验 | `Zod/Valibot` | 商品、兼职、委托、家教、认证、地址等复杂表单统一校验 |
| 接口契约 | `OpenAPI + TypeScript SDK` | 后端维护接口契约，用户端按生成 SDK 接入 |
| 实时能力 | `WebSocket + 站内消息 + 轮询兜底` | App 优先实时连接；微信小程序按能力降级 |

核心判断：**前端统一使用 React 体系，但不强求 App 和微信小程序共用同一套 UI 页面。** 佚名当前业务重心是交易闭环、状态流转、资金展示、审核结果、消息提醒和多角色工作台。更稳的方案是“双壳一核”：微信小程序用 Taro React，原生 App 用 React Native，二者共享接口、领域模型、状态机、表单校验和业务 hooks。

## 2. App 与微信小程序方案对比

| 方案 | App 体验 | 微信小程序 | 代码复用 | 团队成本 | 结论 |
| --- | --- | --- | --- | --- | --- |
| Swift/Kotlin 原生 App + 原生微信小程序 | 最好 | 最好 | 低 | 最高 | 不适合第一版，除非团队充足 |
| Flutter App + 原生微信小程序 | 好 | 需单独开发 | 中低 | 中高 | 不符合 React 技术偏好 |
| Taro React 一套多端 | 中等，RN 侧需验证 | 强 | 高 | 中 | 可作为极致复用方案，但 App 原生体验和插件适配风险更高 |
| React Native App + Taro React 小程序 | 好 | 强 | 中高 | 中 | 已确认采用，React 技术栈统一，体验和稳定性更平衡 |

选择 `React Native + Taro React` 的理由：

1. 满足 React 技术栈偏好，用户端、管理端和共享业务包都可以使用 TypeScript + React 生态。
2. 微信小程序是校园轻量获客入口，Taro React 对小程序页面、组件和构建链路更贴近。
3. App 端有狩猎实时接单、推送、定位、图片上传、商户经营等高频能力，React Native 比小程序跨端壳更适合作为长期 App 基座。
4. 共享接口 SDK、领域枚举、状态机、表单校验和业务 hooks，比强行共享所有 UI 页面更稳。
5. 后续如果 App 体验要求不高，也可以评估 Taro RN 路线；但第一版文档按“微信小程序 Taro + App React Native”规划。

## 3. 目录建议

`client` 目录建议后续按以下结构组织：

```text
client/
  用户端项目开发文档.md
  apps/
    miniapp/             # Taro React 微信小程序，学生/商户/家长共用
    app/                 # React Native App，学生/商户/家长共用
  packages/
    api-client/          # OpenAPI 生成的用户端 SDK
    domain/              # 角色、状态、枚举、金额、时间、权限等共享定义
    hooks/               # 共享业务 hooks，不包含平台 UI
    validators/          # 用户端表单校验规则
    ui-tokens/           # 颜色、间距、字号、状态色等设计 token
  scripts/
    generate-api.ts      # 根据 OpenAPI 生成 SDK
```

第一版可以先创建 `apps/miniapp`、`apps/app` 和最小 `packages/domain`、`packages/api-client`。不要过早做复杂跨端组件库，优先共享业务规则而不是共享所有 UI。

## 3.1 React 统一约束

- 用户端所有新增代码使用 TypeScript。
- 小程序页面使用 Taro React 组件和 API。
- App 页面使用 React Native 组件和 Expo/React Native 能力。
- 服务端数据请求统一走生成的 API SDK，不在页面内手写 URL。
- 服务端状态使用 TanStack Query 管理，端侧 UI 状态和草稿使用 Zustand 管理。
- 金额、时间、状态展示、账号限制和可操作按钮由共享领域规则统一输出。

## 3.2 三端 UI 一致性约束

三端指原生 App、微信小程序和 H5。前端不通过复制页面来保证一致，而通过“同一套产品协议 + 平台适配层”保证一致：

- 角色、2级主模块、底部 Bar 配置统一来自 `packages/domain`，当前由 `clientPrimaryTabs` 输出。
- 颜色、间距、字号、状态色统一沉淀到 `packages/ui-tokens`，三端平台层只做语法映射。
- 业务状态、金额展示、可操作按钮、账号限制统一来自 `packages/domain` 和 `packages/hooks`。
- 页面壳统一采用 App 常见布局：顶部身份/状态区、中间当前 2级模块内容区、底部 Bar、右下角悬浮头像。
- 除“我的”以外，当前角色的 2级主模块全部通过底部 Bar 切换，不再在首页以独立入口卡片跳转。
- “我的”作为右下角悬浮头像入口，点击后进入或展开我的模块；不放入底部 Bar。
- 三端允许组件实现不同，例如 Taro View、React Native View、H5 div，但导航结构、模块命名、状态文案和操作入口必须一致。
- 当前页面迭代先以 H5 为准，除非明确要求同步小程序，否则页面结构、组件拆分和交互调整暂不修改 `apps/miniapp`。
- 前端组件统一使用文件夹管理：`components/组件名/index.tsx` + `components/组件名/index.css`，页面只从组件文件夹入口导入，不再新增同级散落的 `组件名.tsx` 和 `组件名.css`。
- H5 已配置 `unplugin-auto-import`，自动导入声明统一输出到 `apps/h5/src/types/auto-imports.d.ts`；业务类型、组件 Props、页面状态类型统一维护在 `apps/h5/src/types` 目录。

当前代码落点：

```text
packages/domain/src/index.ts   # 角色主导航和我的入口配置
apps/h5/src/App.tsx            # H5 页面壳实现
apps/miniapp/src/pages/home    # Taro 小程序首页实现
```

## 4. 角色与主模块

移动端可登录角色：

- 学生
- 商户
- 家长

角色规则：

- 同一账号不能同时拥有多个普通身份。
- 注册时选择身份；登录时只输入手机号和验证码，由服务端按手机号识别既有账号身份并返回对应首页配置。
- 冻结账号登录后默认跳转解冻申请页。
- 监管状态不可买卖、狩猎、提现。
- 禁言状态不可发布内容、配置营销活动或开启狩猎。
- 封禁状态不可登录。

### 4.1 学生端

| 2级模块 | 第一版核心页面 |
| --- | --- |
| 优选 | 商品/服务列表、详情、下单确认、订单详情、订单状态、售后/投诉入口、提交回收 |
| 兼职 | 兼职列表、详情、报名表、报名状态、报名快照、我的兼职 |
| 委托/狩猎 | 委托发布、狩猎上线、资格验证、狩猎池、接单/报价、进行中委托、履约结算 |
| 我的 | 设置、账户卡片、钱包详情、我的交易、我的记录、进行中列表、家教卡片 |

前端重点：

- 首页优先展示优选和兼职。
- 头像悬浮菜单包含狩猎、发布、余额、更多。
- 流转中订单在头像左侧展示订单快捷按钮。
- 狩猎开启前校验学生认证、身份证照片、学信网截图、押金和信用分状态。
- 我的页面保留狩猎记录，进行中狩猎列表迁移到委托/狩猎模块。

### 4.2 商户端

| 2级模块 | 第一版核心页面 |
| --- | --- |
| 商品 | 销售工作台、销售面板、商品管理入口、配送入口、消息列表 |
| 兼职 | 兼职工作台、发布兼职、进行中的兼职卡片 |
| 营销 | 营销入口和空状态，第一版只预留 |
| 我的 | 设置、账户卡片、认证资料、门店、员工子账号、关注和交易记录 |

前端重点：

- 商户区分主账号和运营子账号。
- 主账号可查看全量内容；子账号只处理售后、产品咨询、商品管理与维护。
- 销售工作台默认展示全部门店汇总，可筛选单门店。
- 商品卡片支持上/下架、隐藏、编辑、价格、库存、限购。
- 订单/配送卡片支持诉求处理弹窗。
- 商户开始销售或发布兼职前需缴纳店铺信用金。

### 4.3 家长端

| 2级模块 | 第一版核心页面 |
| --- | --- |
| 商品 | 商品列表、商品详情、快递配送下单、订单物流、售后、收藏、举报 |
| 家教 | 家教列表、发布家教需求、报名学生列表、学生资料、交换电话、确认招募、结束确认 |
| 我的 | 设置、账户卡片、孩子档案、我的交易、我的关注、进行中列表 |

前端重点：

- 家长商品页与学生商品页基本一致，但配送方式固定为快递。
- 家长可绑定多个孩子，发布家教需求时选择孩子档案。
- 发布家教需求强校验孩子年级和科目。
- 家教服务中改约、终止、爽约均采用一方发起、另一方确认。
- 家教费用按实际服务天数占比结算，不满半天按半天，超过半天按一天。

## 5. 跨端适配原则

### 5.1 必须统一

- 角色和权限判断
- 账号状态限制
- 商品/兼职/委托/家教状态展示
- 订单金额、服务费、物流费、退款金额展示
- 钱包流水和余额展示
- 举报、投诉、售后入口
- 表单必填项和提交前校验

### 5.2 允许差异

| 能力 | App | 微信小程序 |
| --- | --- | --- |
| 登录 | 手机号、验证码，后续可接第三方登录 | 微信授权手机号、手机号验证码 |
| 支付 | 微信、支付宝、余额、组合支付 | 微信支付、余额、组合支付；支付宝受生态限制时不展示 |
| 推送 | App 推送、站内消息、WebSocket | 订阅消息、站内消息、WebSocket/轮询 |
| 定位 | 系统定位、地图 SDK | 微信位置能力 |
| 图片上传 | 相册/相机、压缩上传 | 微信选择图片/拍照 |
| 后台保活 | 可做有限增强 | 不保证后台常驻，狩猎实时能力需降级 |

跨端差异集中在适配层：

```text
platform/
  auth.ts
  payment.ts
  location.ts
  upload.ts
  notification.ts
  realtime.ts
```

业务页面只调用适配层，不直接散落条件编译。

## 6. 关键业务实现

### 6.1 购买

订单主状态：

- 待配送/备货中
- 配送中
- 已送达
- 待确认
- 已完成

前端规则：

- 待确认 48 小时自动完成，由服务端计算倒计时。
- 已完成后 7*24 小时内展示申请退款入口。
- 已完成订单展示评价、申请退款、举报/投诉快捷入口。
- 评价入口跳转商品详情页；可匿名；同一订单只能追评一次。
- 未履约订单买方申请退款时，展示服务端立即退款结果。

### 6.2 兼职

学生侧状态：

- 已报名
- 待筛选
- 未通过
- 已确认/待签到
- 已签到
- 进行中
- 已完成/结算中
- 已结算
- 未签到
- 招募取消
- 异常
- 争议处理

前端规则：

- 报名表支持快捷字段和自定义字段。
- 商户发布兼职可配置是否签到、签到方式和签到保证金。
- 忘签到或未签到进入保证金退还申请和平台介入入口。
- 兼职详情和报名快照必须保留用户提交时字段。

### 6.3 委托/狩猎

前端规则：

- 发布方是委托，服务方是狩猎。
- 委托发布分为报价发布和服务发布。
- 服务发布为固定服务费，服务方可直接接受。
- 报价发布由服务方报价，发布方确认后锁单。
- 超过委托时效仍可领取，但领取后进入发起者确认激活。
- 接受委托后 2 分钟内可取消；5 分钟内可协商取消。
- 狩猎押金、观察期、信用影响均以服务端状态展示。

### 6.4 家教

前端规则：

- 家长可选择孩子档案发布需求。
- 可填写是否试课、试课时长和试课费用。
- 家长可查看学生绩点、学校、专业等资料。
- 家长可拒绝报名者并填写理由。
- 家长可收藏优秀学生。
- 家教完成后学生发起完成，家长确认结束。
- 费用结算进入学生监管账户，观察期后进入可提现钱包。

## 7. 第一阶段开发顺序

1. 工程初始化：Taro React 小程序、React Native App、接口 SDK、基础枚举。
2. 登录注册：登录不选择角色，注册选择学生、商户或家长；校验账号状态限制。
3. 商品购买闭环：列表、详情、下单、支付、订单、售后入口。
4. 商户销售工作台：商品管理、订单、配送、消息。
5. 兼职闭环：发布、报名、筛选、签到、结算。
6. 委托/狩猎闭环：资格验证、发布、狩猎池、接单/报价、履约。
7. 家教闭环：家长发布、学生报名、筛选、确认、完成、结算。
8. 钱包、消息、举报、投诉、账号状态统一增强。

## 8. 风险与约束

| 风险 | 处理方式 |
| --- | --- |
| 小程序后台能力弱，狩猎实时接单受限 | App 做强实时，小程序用订阅消息、站内消息和轮询降级 |
| 支付渠道在不同端能力不一致 | 支付方式由后端按端返回，前端不硬编码 |
| 跨端 UI 细节不一致 | 建立设计 token、基础组件和页面验收截图 |
| 状态机复杂 | 所有状态以后端为准，前端只展示和发起动作 |
| 审核/资金/信用规则频繁变化 | 配置由后端下发，前端保留动态展示能力 |
