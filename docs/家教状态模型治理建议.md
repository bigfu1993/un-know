## 文档信息

| 项目 | 内容 |
| --- | --- |
| 更新时间 | 2026-08-17 |

## 1. 问题背景

`db/tutorStatus.ts` 目前只有一个扁平的 `TutorStatus` 枚举，把"家教需求主状态"和"单条试课申请细分状态"混在一起。更深层的问题是：数据库和后端常量里存的、API 返回给前端的，从头到尾都是**中文展示文案本身**（比如 `TUTOR_APPLICANT_STATUS_REJECTED = "已失效"`），前端再靠 `.includes()` 对这段中文文案做子串匹配来判断状态。这导致：

- 文案不能算稳定契约——历史上已经因为文案调整做过至少 5 次数据迁移（`V18`/`V19`/`V23`/`V25`/`V26`，均是"归一化状态文案"），每次改文案都要联动改数据、改常量、改前端匹配逻辑。
- `.includes()` 子串匹配天然脆弱，容易被别的状态文案里包含相同子串误伤（本次治理前排查就发现"进行中"这个词同时出现在需求主状态和试课过程的判断路径里）。
- 状态和展示文案强耦合，以后要做多语言、或者只是想调整措辞，都要动到判断逻辑本身。

本次收到的新方向：**状态值统一改成稳定 KEY**（不含语义、不随文案调整变化），数据库存 KEY、后端常量是 KEY、API 返回 KEY；中文展示文案只在前端维护一张"KEY → 文案"的映射表，界面渲染时查表取文案，不再从后端拿到手的字符串里做子串解析。

## 2. 现状分析：三种状态字符串来源

排查后发现 `order.status`/`candidate.status` 实际上来自三个不同来源，不是简单的"主状态 + 细分状态"两层嵌套：

### 2.1 学生视角：`tutor_applicant.status` 原始值

学生端 `tutorOrders()`（[TutorWorkspaceAppService.java:859-948](../server/apps/src/main/java/com/unknown/platform/modules/clientworkspace/application/TutorWorkspaceAppService.java#L859-L948)）直接把 `tutor_applicant.status` 原始值透出成 `order.status`。这部分是纯粹的"申请细分状态"，词表对应后端 `TUTOR_APPLICANT_STATUS_*` 常量。

### 2.2 家长候选人列表：`tutor_applicant.status` 原始值

家长审批候选人列表（`TutorApplications.tsx` 的 `candidate.status`）同样是 `tutor_applicant.status` 原始值，跟 2.1 是同一词表。

### 2.3 家长聚合卡片：后端拼装的复合展示串（KEY 化要重点解决的地方）

家长端 `tutorOrders()` 的需求聚合分支（[TutorWorkspaceAppService.java:800-806](../server/apps/src/main/java/com/unknown/platform/modules/clientworkspace/application/TutorWorkspaceAppService.java#L800-L806)）：

```java
String displayStatus = isDemandInProgress
    ? TUTOR_DEMAND_STATUS_IN_PROGRESS + (isServiceEndRequested ? " · " + TUTOR_DEMAND_STATUS_SERVICE_END_REQUESTED : "")
    : tutorDemandStatusLabel(status);
```

家长主卡的 `order.status` 是后端现算的展示字符串，本质是"需求状态 + 当前活跃申请状态"两个维度合成的产物：需求下存在"活跃申请"时展示 `"进行中"`，如果该申请同时处于结束确认阶段，追加成 `"进行中 · 申请结束中"`；否则展示需求原始状态归一化后的结果。

`tools/tutorTrial.ts`/`tools/tutorTaskWorkflow.ts` 里至少两处显式识别这个复合串（`isTutorFormalServiceStatus`、`getTutorTaskStatusLabels`），是故意设计，不是巧合——KEY 化之后不能继续用"复合 KEY 字符串"这种退化方案，否则问题原样保留，只是从中文子串匹配换成 KEY 子串匹配。

## 3. 目标设计：状态值 KEY 化

### 3.1 核心原则

- **KEY 是唯一持久化和跨层传输的值**：数据库列存 KEY（比如 `REJECTED`、`APPLICATION_PENDING`），后端 Java 常量的值是 KEY，API 响应里 `status` 字段也是 KEY。
- **中文展示文案只活在前端**：`db/tutorStatus.ts` 里枚举成员的值就是 KEY；另外维护一张 `Record<枚举, string>` 的展示文案表，界面渲染时查表取文案，不再依赖后端吐出已经拼好的中文串。
- **精确匹配取代子串匹配**：KEY 是原子值，`isTutorXxxStatus` 系列判断函数从 `status?.includes(TutorStatus.X)` 改成 `status === TutorApplicantStatus.X`（或 `Set.has(status)`），不再有"一段字符串里可能塞了两段文案、互相子串误伤"的问题。

### 3.2 两个状态枚举，值改成 KEY，对齐后端命名

| 枚举 | 对齐的后端常量前缀 | 成员（`枚举成员 = KEY`，注释保留中文原文案方便对照） |
| --- | --- | --- |
| `TutorDemandStatus` | `TUTOR_DEMAND_STATUS_*` | `PendingPublish="PENDING_PUBLISH"`、`Recruiting="RECRUITING"`、`InProgress="IN_PROGRESS"`、`ServiceEndRequested="SERVICE_END_REQUESTED"`、`Ended="ENDED"`、`Cancelled="CANCELLED"` |
| `TutorApplicantStatus` | `TUTOR_APPLICANT_STATUS_*` | `ApplicationPending="APPLICATION_PENDING"`、`TrialConfirming="TRIAL_CONFIRMING"`、`Trialing="TRIALING"`、`TrialEndConfirming="TRIAL_END_CONFIRMING"`、`TrialResultProcessing="TRIAL_RESULT_PROCESSING"`、`TrialSettledServicePending="TRIAL_SETTLED_SERVICE_PENDING"`、`ServiceConfirming="SERVICE_CONFIRMING"`、`ServiceSchedulePending="SERVICE_SCHEDULE_PENDING"`、`ServiceScheduleConfirming="SERVICE_SCHEDULE_CONFIRMING"`、`FormalService="FORMAL_SERVICE"`、`ServiceEndConfirming="SERVICE_END_CONFIRMING"`、`SettlementConfirming="SETTLEMENT_CONFIRMING"`、`SettlementRevising="SETTLEMENT_REVISING"`、`SystemSettling="SYSTEM_SETTLING"`、`Ended="ENDED"`、`TrialEnded="TRIAL_ENDED"`、`Rejected="REJECTED"`、`ServiceInvalid="SERVICE_INVALID"`、`Cancelled="CANCELLED"` |

两个枚举各自维护自己的 KEY 空间，不共用；`Ended`/`Cancelled` 在两边字面上撞了同一个 KEY 字符串，但属于不同枚举类型，TypeScript 层面不会混用。

配套新增两张展示文案表（放在同一文件或紧邻的 `tutorStatusLabel.ts`）：

```ts
export const tutorDemandStatusLabel: Record<TutorDemandStatus, string> = {
  [TutorDemandStatus.PendingPublish]: "待发布",
  [TutorDemandStatus.Recruiting]: "发布中",
  // ...
};

export const tutorApplicantStatusLabel: Record<TutorApplicantStatus, string> = {
  [TutorApplicantStatus.ApplicationPending]: "申请试课中",
  // ...
};
```

### 3.3 家长聚合卡片：拆成两个结构化字段，不再拼字符串

后端不再把"需求状态 + 活跃申请状态"拼成一个字符串塞进 `status`，改成两个独立字段：

```json
{
  "status": "IN_PROGRESS",
  "activeApplicantStatus": "SERVICE_END_CONFIRMING"
}
```

- `status` 只承载 `TutorDemandStatus` 语义的 KEY。
- `activeApplicantStatus` 是可选字段，只有存在活跃申请时才有值，承载 `TutorApplicantStatus` 语义的 KEY。
- 前端合并展示（比如"进行中 · 申请结束中"这行文案）在渲染层用两个字段各自查表后拼接，不再需要从一个字符串里反向解析。

这个改动同时让 `getTutorTaskNode` 能真正收窄成强类型入参（`TutorApplicantStatus | { demandStatus: TutorDemandStatus; activeApplicantStatus?: TutorApplicantStatus }`），彻底解决 v1 方案里"因为复合串导致没法强类型化"的问题。

### 3.4 角色投影收口成查表（沿用 v1 结论，不变）

`createTutorTaskModel`（[tutorTaskWorkflow.ts:219-331](../frontend/apps/h5/src/tools/tutorTaskWorkflow.ts#L219-L331)）现状用 `if (role === "student") {...}`、`if (candidate && role === "parent") {...}` 两大段分支各自往 `actions` 集合里加动作。建议把"细分节点 + 角色 → 可用动作集合"整理成一张静态表，`createTutorTaskModel` 只做查表 + 合并 `order.canXxx` 里仍然依赖后端可用性标记的那部分动作，新增状态的角色动作时只改表里一行。

## 4. 迁移路径（自底向上，四层）

1. **后端 Java 常量**：`TUTOR_APPLICANT_STATUS_REJECTED` 等常量的值从中文文案改成 KEY 字符串；`_LEGACY` 常量作为迁移期"旧文案 → 新 KEY"的映射输入，不再是长期存在的常量分支，数据迁移完成、确认无历史脏数据后可以整体删除。
2. **数据库**：新增一个 Flyway 迁移（下一个可用编号，当前最新是 `V29`，所以是 `V30__xxx.sql`），一次性 `UPDATE` 把 `tutor_demand.status`/`tutor_applicant.status` 现有中文文本行（含全部 `_LEGACY` 对应的历史文案）批量映射成新 KEY。这一步之后，旧文案在库里不应再出现。
3. **API 契约**：`ClientOrder.status`、`TutorDemand.status`、`TutorApplicationCandidate.status` 的语义从"展示文案"改为"状态 KEY"；`ClientOrder` 新增 `activeApplicantStatus`（可选）字段承载 3.3 里的第二个 KEY。这一步是前后端联调的分界点，需要前后端同批上线，不能只上一边。
4. **前端**：`db/tutorStatus.ts` 按 3.2 拆枚举并把值改成 KEY，新增展示文案表；`tools/tutorTrial.ts` 全部 17 个 `isTutorXxxStatus` 函数从 `.includes()` 改成 `===`/`Set.has()`；`tools/tutorTaskWorkflow.ts` 的 `getTutorTaskNode`/`getTutorTaskStatusLabels`/`isParentRecruitingTutorOrder` 按 3.3 的结构化入参重写，`createTutorTaskModel` 按 3.4 查表化；`EduCard.tsx:245` 等消费点同步改成 KEY 比较。

这四层必须自底向上、同批上线（数据库先迁移好 KEY，后端跟着切换常量和读写逻辑，API 契约变更后前端才能切枚举），中间不能停留在"数据库是 KEY、前端还在按中文文案匹配"这种半迁移状态——那样两边都读不懂对方。风险和工作量都明显大于 v1 的纯前端命名整理，建议当成一个独立的迁移任务安排具体时间窗口，不要和其他日常需求穿插着做半截。

## 5. 验证方式

- 数据库迁移后：抽查 `tutor_demand`/`tutor_applicant` 表确认不再有中文状态文案残留，历史遗留值也已经归一化成新 KEY。
- 后端切换后：`mvn -o clean compile` + 复用本次会话验证试课拒绝流转时用过的测试账号方式（`/client/auth/register` + 验证码 `000000`）跑一遍主流程，确认接口返回的 `status`/`activeApplicantStatus` 是 KEY 而不是中文。
- 前端切换后：`tsc --noEmit`、`eslint` 全量通过；`grep -rn "\.includes(Tutor" src` 确认没有遗留的子串匹配写法；按主流程（申请 → 排课 → 试课 → 结算 → 正式雇佣 → 结算 → 结束）真实跑一遍，对照重构前后每个节点在学生端和家长端渲染出的文案、按钮集合是否一致。
