## 2. 后端当前状态分析

### 2.1 当前模块现状

| 模块 | 当前职责 |
| --- | --- |
| `modules/clientworkspace` | 聚合订单、兼职、委托/狩猎、家教、商户商品、钱包数据，同时承载大量发布、报价、试课、履约、取消、结算动作 |
| `modules/product` | 商品列表与购买相关能力 |
| `modules/clientprofile` | 用户资料、地址、家教曝光、狩猎认证等用户侧资料能力 |
| `modules/clientchat` | 独立聊天会话、消息、快捷回复 |

`ClientWorkspaceAppService` 当前约 2832 行，包含兼职列表、委托/狩猎任务、狩猎项目、家教需求、家教申请、试课、正式家教、订单聚合等多条业务线。Controller 已经提供 `jobs`、`commission`、`tutor-demands` 等独立接口，但应用服务和响应模型仍集中在 `clientworkspace`。

### 2.2 目标后端分包建议

| 前端业务域 | 建议后端归属 | 迁移范围 |
| --- | --- | --- |
| `home/commission` | `modules/clientcommission` | `hunting_task`、`hunting_task_quote`、委托发布、报价、接受、履约、取消、再次发布、订单映射 |
| `home/commission` 的狩猎项目 | `modules/clienthunting` 或并入 `clientcommission` | `hunting_project`、`hunting_project_stop`、狩猎上线项目、推荐匹配 |
| `home/job` | `modules/clientjob` | `part_time_job` 列表、通用兼职报名/发布的后续能力 |
| `home/edu` | `modules/clientedu` | `tutor_demand`、`tutor_applicant`、试课安排、试课结束、正式雇佣、家教日程和结算流程 |
| `home/shop` | 保持 `modules/product`，必要时改名为 `modules/clientshop` | 商品/优选列表、购买和商品订单 |
| 聚合工作台 | 保留 `modules/clientworkspace` | 只负责调用各业务域服务组装工作台聚合响应，不再直接承载业务写操作 |

### 2.3 推荐迁移顺序

1. 提取后端状态常量和纯查询 mapper：先把散落在 `ClientWorkspaceAppService` 的状态判断、金额格式化、行映射提取到业务域私有类，不改变接口。
2. 拆服务不改接口：新增领域 application service，由 `ClientWorkspaceAppService` 委托调用，保持原 controller 路径和响应不变。
3. 拆模型：将 `PublishHuntingTaskRequest`、`PublishTutorDemandRequest` 等请求响应模型迁移到目标模块，保留兼容 import 或一次性同步 controller、api-client、domain、hooks。
4. 拆 controller：在前端接口和 hooks 已稳定后，再把 URL 按业务域迁移；旧 URL 保留兼容层一个版本。
5. 删除聚合服务中的业务写逻辑：`clientworkspace` 只保留聚合查询和跨域组合。

以上步骤均需要每批执行 `mvn -q -DskipTests compile`，涉及接口路径变化时同步 `frontend/apps/packages/api-client`、`frontend/apps/packages/hooks` 和 PRD。

## 3. 数据库设计风险分析

### 3.1 当前主要表归属

| 表 | 当前用途 | 建议归属 |
| --- | --- | --- |
| `product`、`purchase_order` | 优选/商品和购买订单 | `shop/product` |
| `part_time_job` | 通用兼职列表 | `job` |
| `hunting_task`、`hunting_task_quote` | 委托任务、报价、履约状态 | `commission` |
| `hunting_project`、`hunting_project_stop` | 狩猎上线项目和下一站计划 | `commission/hunting` |
| `tutor_demand`、`tutor_applicant` | 家教需求、家教申请、试课和正式雇佣状态 | `job/edu` |
| `client_address` | 用户地址 | `profile`，被发布、购买和家教模块引用 |
| `app_user` | 用户账号、角色、认证状态、曝光开关 | `auth/profile`，认证扩展建议逐步拆表 |
| `wallet_account`、`wallet_record` | 钱包余额、观察期、账单 | `wallet` |
| `chat_conversation`、`chat_message`、`chat_quick_action` | 独立聊天能力 | `chat` |

### 3.2 需要优化但不应直接改的高风险项

1. `tutor_applicant` 的试课安排当前以 `availability`、`trial_start`、`trial_end`、`trial_half_day` 等字符串承载，多日、多时段、冲突校验和预览渲染都不稳定。建议新增 `tutor_trial_schedule` 表或 `JSONB` 字段承载结构化日期、上午/下午/晚上、开始结束时间、来源方和版本号。
2. `tutor_demand` 的 `period_start`、`period_end`、`school_tags` 等字段是字符串，后续周期排课、孩子选择、筛选和结算会需要结构化字段或关联表。
3. `app_user` 同时承载家教认证状态、狩猎认证状态、家教曝光开关。认证资料增长后建议拆分为 `tutor_certification`、`hunting_certification` 或统一 `user_certification` 表，保留审核记录和重新认证版本。
4. 委托/狩猎和家教状态值仍有历史兼容值，需要以状态常量、迁移脚本和数据校验逐步收敛，避免前后端继续散落字符串。
5. 订单列表目前由购买订单、委托任务、家教需求等业务表聚合生成。建议后续新增统一订单索引表或订单视图，承接搜索、筛选、历史记录、再次发布、结算和售后查询。

### 3.3 数据库迁移原则

1. 不修改已经应用的 Flyway 历史迁移文件。
2. 任何表结构变化必须新增更高版本 `V*.sql`。
3. 数据结构规范化需要先兼容旧字段读写，再切换后端读新字段，最后在后续版本清理旧字段。
4. 涉及状态字段收敛时，需要先写数据清洗迁移，再更新 Java 常量和前端状态展示。
5. 涉及订单、钱包、认证、履约状态的迁移必须准备回滚或补偿方案，不做一次性大改。

## 4. 对话内容总结提取

### 4.1 已沉淀为长期规范的要求

1. 默认中文沟通，新增和维护的代码注释使用中文。
2. 变量、方法、类、组件、类型、关键常量按标准注释规则补充有效注释。
3. H5 使用全局别名，跨目录引用不再使用相对路径。
4. H5 可复用类型集中在 `frontend/apps/h5/src/types`，通过 auto-import 或全局声明使用；被自动导入覆盖的类型移除显式 import。
5. 每次产品功能变化同步更新 `docs/产品需求文档.md`。
6. 修改后必须检验相关功能是否正常运行；不涉及后端代码、配置、数据库迁移或运行时依赖时，不重启后端。
7. 本地运行按 `AGENTS.md` 和 `server/运行部署文档.md` 的固定流程，不重复发散排查。
8. 真实业务状态必须由后端接口和数据库闭环，不用 H5 本地状态替代。
