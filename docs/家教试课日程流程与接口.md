# 家教试课日程流程与接口

> 更新时间：2026-09-01
> 范围：家长在统一申请列表提交试课日程后，到学生确认、试课进行和试课结束结算的当前真实实现。
> 边界：家长提交请求和学生端进行中读取均使用结构化日期与时间段；历史摘要仅用于兼容尚未回填结构化数据的旧记录。

## 1. 当前主流程

| 步骤 | 发起方 | 操作与接口 | 申请状态迁移 | 结果 |
| --- | --- | --- | --- | --- |
| 1 | 家长 | `POST /client/workspace/tutor-demands/{demandId}/applications/{applicationId}/trial` | `APPLICATION_PENDING -> TRIAL_CONFIRMING`；已处于 `TRIAL_CONFIRMING` 时允许修改日程并保持原状态 | 写入试课日程，学生端出现“日程”入口 |
| 2 | 学生 | 查看 `GET /client/workspace/ongoing` 返回的进行中事项 | 保持 `TRIAL_CONFIRMING` | `canAgreeTrial=true`、`canOpenTrialSchedule=true` 时可查看并同意 |
| 3 | 学生 | `POST /client/workspace/tutor-applications/{applicationId}/trial/confirm`，无请求体 | `TRIAL_CONFIRMING -> TRIALING` | 进入“试课中” |
| 4A | 学生 | `POST /client/workspace/tutor-applications/{applicationId}/trial/end-request` | `TRIALING -> TRIAL_END_CONFIRMING` | 等待家长提交试课结算 |
| 4B | 家长 | `POST /client/workspace/tutor-applications/{applicationId}/workflow-action`，`action=request_trial_result` | `TRIALING -> SETTLEMENT_CONFIRMING` | 家长直接提交试课费用，可选是否正式雇佣，等待学生确认费用 |
| 5 | 家长 | 学生先发起结束时，调用 `workflow-action`，`action=confirm_trial_end` | `TRIAL_END_CONFIRMING -> SETTLEMENT_CONFIRMING` | 写入试课费用和可选雇佣决策 |
| 6 | 学生 | `workflow-action`，`action=confirm_settlement` | 按家长雇佣决策进入 `SERVICE_CONFIRMING`、`TRIAL_ENDED` 或 `TRIAL_SETTLED_SERVICE_PENDING` | 试课费用确认完成，进入正式雇佣或结束分支 |

补充分支：`TRIAL_CONFIRMING` 阶段仍保留学生取消申请接口；`update_trial_availability` 和“日程冲突”界面在当前代码中仍作为兼容分支存在，但学生可用时间不属于当前主链路，也不参与家长提交试课日程的范围校验。

## 2. 家长提交接口

### 2.1 请求

```http
POST /api/client/workspace/tutor-demands/{demandId}/applications/{applicationId}/trial
Content-Type: application/json
Authorization: Bearer <accessToken>
```

```json
{
  "dates": [
    {
      "date": "2026-09-06",
      "timeRanges": [
        { "start": "09:00", "end": "10:30" }
      ]
    },
    {
      "date": "2026-09-08",
      "timeRanges": [
        { "start": "18:00", "end": "20:00" }
      ]
    }
  ]
}
```

| 字段 | 当前含义 | 约束 |
| --- | --- | --- |
| `dates` | 本次提交的完整试课日期集合 | 必填；1 至 3 个不同日期，提交顺序不影响结果 |
| `dates[].date` | 单个试课日期 | 必填；`YYYY-MM-DD` |
| `dates[].timeRanges` | 当天全部有效试课时间段 | 必填且非空 |
| `start`、`end` | 单个时间段起止时间 | 必填；`H:mm` 或 `HH:mm`，必须落在 `08:00-22:00` 内并使用 10 分钟刻度，结束时间必须晚于开始时间 |

前端 `CalendarTime` 内部实际维护更完整的 `TrialScheduleValue`：

```ts
interface TrialScheduleValue {
  scheduleDraft: Record<
    string,
    Record<"morning" | "afternoon" | "evening", {
      enabled: boolean;
      start: string;
      end: string;
    }>
  >;
  plan: {
    dates: Array<{
      date: string;
      timeRanges: Array<{ start: string; end: string }>;
    }>;
    summary: string;
  };
}
```

实际安排日期由 `scheduleDraft` 中的有效时间段派生为 `plan.dates`，不再维护独立日期数组。提交时只发送 `plan.dates`；`summary` 仅用于 H5 比较日程是否发生变化，`scheduleDraft` 不直接进入接口。发布家教时选择的计划日期始终使用 `plannedDates`，后续制定试课日程时继续通过同名字段回显；实际试课和正式课程分别通过 `testedDatas`、`arrangedDatas` 展示，不写入 `plannedDates`。

“使用模板”由 `CalendarPanel` 内部 Switch 控制，但开关是否出现必须由当前进行中 `ClientOrder` 与所选申请人的流程能力共同决定。开启后首次点击非当前日期只切换查看，再次点击当前日期才把用户时间模板应用到当天或清空当天，拖拽则批量处理范围日期；试课满 3 天后锁定新增和拖拽，但保留取消已有日期的入口，正式课程不设该上限。发布计划日历不展示模板 Switch。

家长端不再维护独立试课列表。每个申请人始终保留在同一需求的“申请列表”中，卡片按该申请自己的状态与日程原地更新；同一需求允许多名申请人分别制定试课计划，申请日程仍以 `applicationId` 独立存储。

打开制定或调整试课日程前，H5 调用 `GET /api/client/workspace/ongoing/tutor/trial-occupancy?excludeApplicationId={applicationId}`，读取该家长账号在所有家教需求下仍有效的其他试课日程。占用按上午 `08:00-12:00`、下午 `12:00-18:00`、晚上 `18:00-22:00` 三个完整时段计算：任一已有时间范围与某时段相交，该时段即整体不可为其他申请人安排。查询排除当前申请，允许调整其自己的原日程；模板应用命中占用时段时整次应用失败，不部分写入。

### 2.2 后端处理

1. 从会话读取当前用户，校验其为该 `tutor_demand` 的发布家长。
2. 拒绝已结束或已取消的需求。
3. 仅允许更新 `APPLICATION_PENDING` 或 `TRIAL_CONFIRMING` 的申请。
4. 校验 `dates` 为 1 至 3 个不同日期，每天至少一个时间段，日期/时间格式有效，起止时间落在 `08:00-22:00` 内且使用 10 分钟刻度，结束时间晚于开始时间；当前不读取 `availability`。
5. 在同一事务内锁定家长账号，查询该账号所有启用家教需求下处于 `TRIAL_CONFIRMING`、`TRIALING`、`TRIAL_END_CONFIRMING` 的其他申请日程，并排除当前 `applicationId`；请求日程与任一已占用的上午、下午或晚上时段冲突时，返回 `TUTOR_TRIAL_SCHEDULE_CONFLICT`，不更新申请或日程。
6. 按日期及每天的开始时间排序，由后端生成结构化 `schedule_dates`，并派生 `schedule_start`、`schedule_end` 和兼容展示用的标准中文 `schedule_summary`；申请状态更新为 `TRIAL_CONFIRMING`。
7. 按申请与阶段唯一键，向 `tutor_application_schedule` 执行 upsert：`stage=trial`、`schedule_dates=<本次完整日程 JSON>`、`created_by_role=parent`；新提交不再写 `tutor_applicant.trial_*` 旧列。
8. 返回最新 `TutorDemand`，发布 `ongoing_orders_changed` 事件；前端 mutation 同时失效 workspace、进行中、兼职列表、申请人和试课占用查询。

### 2.3 响应

接口统一返回：

```json
{
  "code": "OK",
  "message": "OK",
  "data": {
    "id": "TD...",
    "status": "发布中",
    "plannedDates": ["2026-09-06", "2026-09-08"],
    "applicants": [
      {
        "id": "TA...",
        "status": "TRIAL_CONFIRMING",
        "trialSchedule": "2026年9月6日 09:00-10:30；2026年9月8日 18:00-20:00"
      }
    ]
  },
  "requestId": "..."
}
```

`data` 的实际结构是完整 `TutorDemand`；示例只列出本流程关键字段。前端 mutation 当前不直接消费该响应，而是通过查询失效重新拉取页面所需数据。

## 3. 持久化结构

当前运行时以阶段日程表作为唯一来源：

| 位置 | 字段 | 用途 |
| --- | --- | --- |
| `tutor_application_schedule` | `tutor_applicant_id`、`stage`、`schedule_dates`、`schedule_start`、`schedule_end`、`schedule_summary`、`created_by_role`、`enabled` | 试课提交、学生确认和页面读取的日程来源；`schedule_dates` 保存结构化日期与时间段，`(tutor_applicant_id, stage)` 唯一 |
| `tutor_applicant` | `trial_start`、`trial_end`、`trial_half_day` | 只保留数据库历史兼容；V28 已把存量摘要迁入阶段日程表，新代码不再读写 |

学生确认试课时也只检查 `tutor_application_schedule.stage=trial` 是否存在有效摘要，不再依赖三个旧列是否非空。

## 4. 学生端读取结构

学生端 `GET /api/client/workspace/ongoing` 返回 `ClientOrder`。处于 `TRIAL_CONFIRMING` 且已存在试课日程时，关键字段为：

```json
{
  "id": "TA...",
  "status": "TRIAL_CONFIRMING",
  "canAgreeTrial": true,
  "canOpenTrialSchedule": true,
  "canCancelTutorApplication": true,
  "plannedDates": ["2026-09-06", "2026-09-07", "2026-09-08"],
  "testedDates": [
    {
      "date": "2026-09-06",
      "timeRanges": [
        { "start": "9:00", "end": "10:30" }
      ]
    }
  ],
  "detail": "... · 试课安排：2026年9月6日 09:00-10:30"
}
```

`plannedDates` 表示发布家教时确定的计划范围，`testedDates` 表示当前申请真实提交的试课日期与时间段。学生进行中卡片只展示一个“日程”入口；同一个只读日历用 `.planned` 回显计划日期，并用 `testedDates` 生成试课角标、分时段图标和当天时间明细。新数据不再从 `detail` 反向解析；当历史记录的 `schedule_dates` 仍为空数组时，后端才从 `schedule_summary` 兼容生成 `testedDates`。

## 5. 当前设计问题

1. `TutorDemand.status` 在该接口响应中是中文展示文案，而 `applicants[].status` 是稳定状态 KEY，同一响应内状态口径不一致。
2. mutation 收到完整 `TutorDemand` 后没有直接消费，仍统一失效四组查询；响应体成本和前端刷新策略没有形成单一明确契约。
3. `update_trial_availability`、“日程冲突”界面以及 `docs/家教兼职流程图.md` 中的学生可用时间链路仍作为兼容遗留存在，但当前产品规则不再收集学生可试课时间。这部分需要单独决定是彻底删除，还是重新定义后再恢复，不能继续保持半启用状态。

## 6. 后续提交响应建议（未实施）

请求结构化已经完成。后续建议让响应返回申请工作流快照，或成功后不返回业务对象并统一重新查询；不要继续返回前端随后丢弃的完整需求：

```json
{
  "applicationId": "TA...",
  "demandId": "TD...",
  "status": "TRIAL_CONFIRMING",
  "trialSchedule": {
    "stage": "trial",
    "scheduleStart": "2026-09-06",
    "scheduleEnd": "2026-09-08",
    "dates": [
      {
        "date": "2026-09-06",
        "timeRanges": [
          { "start": "09:00", "end": "10:30" }
        ]
      }
    ]
  },
  "allowedActions": ["confirm_trial_start", "cancel_application"]
}
```

该结构相对当前完整 `TutorDemand` 响应的收益：

1. 提交接口可直接返回被修改的申请快照，不再返回前端随后丢弃的完整需求。
2. 权限动作随申请快照返回，减少多个 `can*` 布尔值组合出非法状态的风险。

`ClientOrder.testedDates`、H5 日历消费和数据库结构化持久化已经实施；后续只处理提交接口响应体策略及对应回归测试。
