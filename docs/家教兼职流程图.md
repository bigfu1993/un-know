# 家教兼职流程图

> 更新时间：2026-07-16
> 范围：家长发布家教兼职、学生申请试课、试课结束确认、正式雇佣确认、正式服务结束/完成确认。
> 说明：第 3 节直接引用 SVG 流程图。本文描述产品目标流程，具体落库状态、接口和前端入口需要以该流程为准逐步收敛。

## 1. 状态口径

家教兼职需要区分“家长发布需求主状态”和“学生申请/服务状态”。家长端发布后，需求可以保持“发布中”，同时叠加某个学生的“试课中”状态；只有正式兼职日程被学生确认后，才进入正式家教服务。

| 层级 | 状态 | 归属 | 说明 |
| --- | --- | --- | --- |
| 需求主状态 | 发布中 | 家长端需求 | 家长已发布家教兼职，仍可接收学生申请 |
| 申请状态 | 申请试课中 | 学生申请 | 学生已申请试课，等待家长同意或拒绝 |
| 申请终态 | 已失效 | 学生申请 | 家长拒绝试课后，学生端该申请失效；家长需求仍为发布中 |
| 日程确认 | 试课日程确认中 | 学生申请 | 家长同意试课后基于学生可试课时间提交试课日程，学生确认后才进入试课中；未确认时由学生修改可试课时间并重新提交试课申请 |
| 叠加状态 | 试课中 | 学生申请、家长需求叠加展示 | 家长同意试课后，学生端进入试课中；家长端需求主状态仍非正式进行中，只叠加试课中 |
| 试课确认 | 结束试课确认中 | 学生申请 | 学生发起结束试课后等待家长确认；家长发起结束试课时跳过该确认 |
| 试课结果决策 | 试课结果处理 | 家长端试课列表 | 家长发起结束试课，或学生发起结束试课且家长确认后进入；家长处理是否正式雇佣 |
| 试课结算确认 | 结算确认中 | 学生申请 | 家长不正式雇佣且不继续发布时发起结算确认，等待学生确认 |
| 试课终态 | 结算结束/试课已结束 | 学生申请 | 学生确认结算后，本次试课结束 |
| 服务确认 | 家教服务确认中 | 正式服务 | 家长在试课结束时发起正式雇佣确认，等待学生同意 |
| 服务排期 | 兼职日程待提交 | 正式服务 | 学生同意正式雇佣并提交可兼职周期后，等待家长提交兼职日程 |
| 服务排期 | 兼职日程确认中 | 正式服务 | 家长提交兼职日程后，等待学生确认；未确认时由学生修改可兼职周期并重新提交 |
| 服务主状态 | 正式家教服务 | 双方正式服务 | 学生确认兼职日程后，进入正式家教服务；该兼职不可被查看和申请 |
| 服务排期 | 日程调整 | 正式服务 | 正式家教服务中需要调整日程时，回到兼职日程确认节点重新确认 |
| 服务结算 | 系统结算中 | 正式服务 | 任一方发起结束后，由系统计算本次服务结算金额 |
| 服务确认 | 结算确认中 | 正式服务 | 系统或家长提交结算金额后，等待学生确认 |
| 服务确认 | 结算修改中 | 正式服务 | 学生不确认结算金额后，等待家长端修改结算金额并提交 |
| 需求终态 | 已结束 | 家长端需求、正式服务 | 学生确认结算后进入最终关闭状态 |

## 2. 角色视图与操作边界

家教业务流程主要有三个状态展示主模型，学生端进行中卡片不再维护第四套独立状态。状态展示和按钮权限必须按主模型计算，不能只用一个总状态直接渲染所有卡片。

| 状态展示主模型 | 卡片对象 | 状态来源 | 主要展示状态 | 当前用户可执行操作 |
| --- | --- | --- | --- | --- |
| 家长端进行中列表卡片 | 家长发布的家教兼职需求 | 需求主状态 + 申请聚合状态 + 试课/服务叠加状态 | 发布中、发布中 + 申请数、发布中 + 试课中、发布中 + 试课结果处理、发布中 + 家教服务确认中、发布中 + 兼职日程待提交、发布中 + 兼职日程确认中、正式家教服务、系统结算中、结算确认中、结算修改中、已结束 | 电话、消息、申请列表、试课列表、取消发布、提交兼职日程、发起结束、修改结算金额、查看订单 |
| 家长端申请列表卡片 | 某个学生的申请 | 申请状态 | 申请试课中、试课日程确认中、已失效；日程确认后从申请列表移入试课列表 | 查看学生信息、可试课时间、同意试课、拒绝试课、制定试课日程 |
| 家长端试课列表卡片 | 某个学生的试课或正式服务 | 试课/服务状态 | 试课中、结束试课确认中、试课结果处理、结算确认中、结算结束/试课已结束、家教服务确认中、兼职日程待提交、兼职日程确认中、正式家教服务、系统结算中、结算确认中、结算修改中、已结束 | 电话、消息、发起结束试课、确认结束试课、发起正式雇佣确认、选择是否继续发布、发起结算确认、重新发起结算确认、提交兼职日程、等待学生确认、发起结束、修改结算金额 |

学生端进行中卡片按阶段映射到上述三个主模型：

| 学生端阶段 | 状态展示来源 | 显示规则 |
| --- | --- | --- |
| 申请阶段 | 家长申请列表中的申请者卡片状态 | 学生端展示申请试课中、已失效等申请状态；按钮按学生角色收敛为电话、消息、查看结果 |
| 试课阶段 | 家长试课列表中的学生卡片状态 | 学生端展示试课中、结束试课确认中、结算确认中、结算结束/试课已结束等试课状态；按钮按学生角色收敛为电话、消息、发起结束试课、等待家长确认、确认结算或查看结果 |
| 正式雇佣阶段 | 家长进行中的列表卡片状态 | 学生端展示家教服务确认中、兼职日程待提交、兼职日程确认中、正式家教服务、系统结算中、结算确认中、结算修改中、已结束等正式服务状态；按钮按学生角色收敛为同意或不同意正式雇佣、提交可兼职周期、确认兼职日程、修改可兼职周期、发起结束、确认结算或要求修改 |

操作按钮还需要区分发起方和确认方：

| 确认类状态 | 发起方看到 | 另一方看到 |
| --- | --- | --- |
| 结束试课确认中 | 等待家长确认，可查看详情 | 确认结束试课 |
| 结算确认中 | 家长端等待学生确认，可重新发起结算确认 | 学生端确认结算，或要求家长重新发起结算确认 |
| 家教服务确认中 | 家长端等待学生确认，可查看正式雇佣信息 | 学生端同意正式雇佣并提交可兼职周期、不同意正式雇佣并选择原因 |
| 兼职日程确认中 | 家长端等待学生确认，可修改兼职日程 | 学生端确认兼职日程、修改可兼职周期 |
| 结算确认中 | 系统或家长已提交结算金额，等待学生确认 | 学生端确认结算或要求修改 |
| 结算修改中 | 学生不确认结算金额，等待家长修改金额 | 家长端修改结算金额并提交 |

## 3. 编号主链路

先按图中编号自上而下阅读主链路，再回到第 4 节查看每一步在不同卡片里的展示位置。

绘制规则：

- 下一步骤默认与上一步骤保持同一竖直轴线；同一横行只放相同编号或同一编号的不同分支，画布不够时扩展画布，不压缩节点。
- 每一层级采用一致的上下间距，保证编号从上到下可顺序扫描。
- 菱形判断必须明确左右分支，判断文案只写在连线上，节点只表达业务动作；左右出线连接下一节点时，终点必须从目标节点顶部中心接入，不得从目标节点侧边接入。
- 子节点必须落在父节点中轴线两侧或与父节点中轴线对齐：单一下一流程沿中轴线向下，判断分支围绕中轴线左右对称展开；如果子节点内容变多或节点变宽，优先增加父节点延伸出的横线长度，不破坏子节点轴线关系。
- 判断节点的“否”分支线条和箭头统一使用红色；“是/否”分支文字放在箭头落点一侧的竖线旁，距离竖线约 `20px`，避免贴在菱形或水平分叉线上。
- 流程图文字统一字号；“否”分支落点为矩形节点时，矩形和节点文字统一使用 `0.8` 透明度。
- 分叉横线左右长度必须一致，并以 `10` 为单位递增；目标节点距离不足时优先增加分叉单位长度或扩展画布，不画成长短不一的左右分支。
- 单轴或居中菱形参考步骤 `3` 的左右分支画法；多轴场景优先保证当前节点语义、线色和目标一致，`否` 分支必须使用红色，例如当前 `20` 结算确认左是右否，`22` 学生确认右否回流。
- 同阶段修改采用实线回流，跨阶段回退采用虚线长线。

## 5. 场景规则

### 6.1 发布与申请

1. 家长发布家教兼职后，家长端需求主状态为“发布中”。
2. 学生在兼职列表申请试课时必须提交可试课时间，学生端生成“申请试课中”记录。
3. 家长端申请列表出现对应申请，需求主状态仍为“发布中”。
4. 同一学生对同一需求不得重复申请；重复申请应由后端接口拦截。
5. 家长端进行中列表卡片展示“发布中 + 申请数”，申请列表卡片展示具体学生的“申请试课中”。
6. 学生端处于申请阶段时，进行中卡片复用“家长申请列表中的申请者卡片状态”口径，展示“申请试课中”等申请状态。

### 6.2 拒绝试课

1. 家长拒绝试课后，学生端该申请变为“已失效”。
2. 家长端需求仍为“发布中”，不进入正式进行中。
3. 被拒绝申请不再参与试课、正式雇佣和结束/完成确认。
4. 家长端申请列表卡片可以从可操作列表移除，或仅作为历史展示“已失效”，但不能继续展示同意试课操作。

### 6.3 同意试课与日程确认

1. 学生申请试课时维护可试课时间；家长申请列表卡片必须展示该学生可试课时间。
2. 家长选择同意试课后，基于学生可试课时间提交试课日程，申请者卡片进入“试课日程确认中”。
3. 学生确认试课日程前，学生端仍处于申请阶段，进行中卡片复用“家长申请列表中的申请者卡片状态”口径。
4. 学生不确认试课日程时，需要由学生修改可试课时间并重新提交试课申请，流程回到步骤 2 等待家长重新处理。
5. 学生确认试课日程后，才进入“试课中”；学生端进入试课阶段，进行中卡片复用“家长试课列表中的学生卡片状态”口径。
6. 家长端需求主状态仍为“发布中”，但需要叠加展示“试课中”。
7. 试课中不是正式家教进行中，不应触发正式家教服务的完成/结束按钮。
8. 家长端可以同时保留发布中需求和试课中申请的双状态展示。
9. 家长端申请列表卡片在日程确认前保留该申请；日程确认后移入试课列表卡片，试课列表卡片展示该学生“试课中”。
10. 家长端进行中列表卡片展示“发布中 + 试课中”，并提供试课列表入口。

### 6.4 结束试课确认

1. 试课中家长或学生都可以发起结束试课，但两种发起方链路不同。
2. 家长发起结束试课时，不再进入对方确认环节，直接进入步骤 11 的试课结果处理。
3. 学生发起结束试课时，进入“结束试课确认中”，需要家长在试课列表卡片中确认。
4. 步骤 10 是“家长确认试课结束”的流程节点，确认后通过横线汇入步骤 9B 到步骤 11 的竖线，进入步骤 11 的试课结果处理。
5. 步骤 10 不回到步骤 8；确认前保持“结束试课确认中”，确认后进入步骤 11。
6. 试课结束不等于家长需求结束；家长需要在不正式雇佣时判断是否继续发布。

### 6.5 正式雇佣确认

1. 家长在试课结束时选择是否正式雇佣。
2. 若不正式雇佣，学生端本次试课变为“已结束”。
3. 不正式雇佣后，家长端需要继续判断是否继续发布；继续发布则需求回到“发布中”，不继续发布则由家长发起结算确认。
4. 学生结算确认时，是则进入“结算&结束”，否则回到 13B 由家长重新发起结算确认。
5. 若正式雇佣，由家长发起正式雇佣确认，状态进入“家教服务确认中”，等待学生同意。
6. 学生同意正式雇佣后，进入“家长学生确认兼职日程”节点，节点内完成可兼职周期提交、家长提交兼职日程和学生确认兼职日程。
7. 兼职日程确认完成后，双方才进入正式家教服务，该兼职不可被查看和申请。
8. 学生不同意正式雇佣后，需要判断不同意原因是否为薪资：若是薪资原因，回到 12A 由家长重新发起正式雇佣确认；否则正式雇佣失效，家长需求回到或保持“发布中”。
9. “家教服务确认中”由家长端试课列表卡片发起；进入该阶段后，学生端进行中卡片转为复用“家长进行中的列表卡片状态”口径，并承接正式雇佣确认和兼职日程确认操作。
10. 兼职日程确认完成后，家长端进行中列表卡片主状态才变为“正式家教服务”，学生端也继续按该正式服务口径展示。

### 6.6 正式服务结束与完成

1. 正式家教服务后的日程调整入口由步骤 `16` 进入 `17`，`17` 使用虚线节点表示非终态调整。
2. `17` 的虚线回流指向 `15A`，调整后重新完成家长学生兼职日程确认。
3. `17` 下方进入 `18` 发起结束，原 `18` 之后的家长/学生发起结束、提前结束、继续招募和服务完成旧节点全部移除。
4. `18` 发起结束后进入 `19` 系统结算，由系统计算本次服务结算金额。
5. `19` 下方进入 `20` 结算确认判断；学生确认结算时直接走同轴的 `23` 结算&结束。
6. 学生不确认结算时走 `21`，由家长端修改结算金额并提交。
7. `21` 下方进入 `22` 学生确认；`22` 与 `23` 保持同一行，学生确认时从左侧链路接入 `23` 右侧并结算&结束。
8. `22` 学生确认选择否时，回到 `21`，由家长端再次修改结算金额并提交，直到学生确认。
9. 正式服务阶段，学生端进行中卡片复用家长进行中列表卡片的服务状态口径；家长端试课列表卡片如继续承接服务卡片，也必须与该正式服务口径保持一致。

## 7. 实现提示

1. 后端应把流程状态作为真实源头，前端只消费状态和可操作按钮。
2. 建议至少拆分需求主状态、申请/试课状态、正式服务状态，避免把“发布中 + 试课中”压成一个单字段。
3. 前端家长端卡片需要支持主状态和叠加状态同时展示。
4. 学生端进行中卡片按阶段映射状态源：申请阶段同申请者卡片，试课阶段同试课学生卡片，正式雇佣阶段同家长进行中列表卡片。
5. 任意确认类状态必须记录发起方、确认方、发起时间和确认结果，避免双方同时操作造成状态错乱。
6. 现有实现中如仍使用“家教招募中”“试课确认中”“取消试课确认中”等旧状态，需要迁移或兼容到本文状态口径；“试课确认中”统一按“试课日程确认中”理解。
7. 前端任务模型建议以“三个状态展示主模型 + 学生端阶段映射 + 当前角色 + 当前用户是否发起方”作为入参，输出展示状态、按钮集合和列表归属。
8. 后端接口响应建议直接返回三个主模型的可见状态、可执行操作和学生端阶段映射信息，避免 H5 在不同组件里重复推导权限。

## 8. 待确认问题

1. 正式雇佣因非薪资原因失效后，学生端展示“已失效”还是“已结束”。
2. 多个学生同时试课时，家长端叠加状态展示为单个“试课中”还是显示试课中数量。
